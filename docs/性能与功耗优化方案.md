# 性能与功耗优化方案

> 日期：2026-08-13  
> 状态：**待确认后实施**  
> 范围：仅优化运行时资源释放、网络请求终止和无效唤醒；不改变现有产品需求、Provider
> 语义、刷新口径或 OAuth 行为。  
> 当前证据：本文来自代码静态审查。未执行构建、自动化测试、模拟器或真机性能测试。

## 1. 结论与建议

### 1.1 是否需要优化

需要，但不需要大规模重构。

当前应用没有后台刷新、后台 Service、WakeLock、大列表、图片解码或持续动画，正常静置时的
性能和功耗基线已经比较克制。最值得处理的是两类异常路径：

1. Android OAuth 使用的 Custom Tabs 服务在登录结束后没有立即解绑，可能让浏览器服务和
   Binder 会话继续驻留到 Activity 销毁。
2. 网络请求外层的 15 秒 `Future.timeout` 只会停止等待，不会取消底层请求；弱网、代理异常
   或半开连接下，请求可能在超时结果返回后继续占用 socket 和移动网络资源。

这两项都可以在**不改变正常功能**的前提下修复，建议实施。

退避期每分钟重复进入刷新入口并触发界面通知也值得顺手收敛。它不发网络请求，收益低于前
两项，但修复范围小、功能风险低，建议一起实施。

其余可优化点——倒计时 Timer、根节点重建、Claude profile 补取——在当前数据规模和刷新
频率下收益有限，且部分改法会改变现有业务行为。本轮不建议动，除非真机数据证明它们已经
成为主要耗电来源。

### 1.2 推荐范围

| 优先级 | 项目 | 是否实施 | 原因 |
|---|---|---:|---|
| P1 | Android OAuth 终态释放 Custom Tabs 资源 | 是 | 真实资源生命周期缺口，正常功能无需依赖终态后的绑定 |
| P1 | 15 秒超时真正取消底层 HTTP 请求 | 是 | 避免弱网请求在超时后继续运行或与后续重试重叠 |
| P2 | 退避期跳过无效的自动刷新入口和通知 | 是 | 保持原请求时机不变，同时减少每分钟唤醒和整页重建 |
| P3 | `resetsAt` 为空或已过期时不启动倒计时 Timer | 可选 | 改动小，但收益很低，可在前三项稳定后再决定 |
| 暂缓 | 合并全部倒计时 Timer | 否 | 当前仅少量窗口，状态架构改动大于收益 |
| 暂缓 | 拆分 `AppController` / `MaterialApp` 监听 | 否 | 通知频率很低，重构会扩大状态一致性风险 |
| 暂缓 | 降低自动刷新频率或减少 Provider 请求 | 否 | 会影响数据新鲜度、Reset Credits 或用户设置 |
| 暂缓 | 停止未知套餐的 Claude profile 补取 | 否 | 会改变“缺失信息后续继续补取”的现有需求 |

### 1.3 可以预期的收益

正常网络、正常登录、应用短时间打开时，优化前后差异不会很大；当前应用本来就不是持续高
负载程序。主要收益集中在：

- Android 完成或退出 OAuth 后，不再由本应用长期持有浏览器服务连接。
- 网络异常时，15 秒到期即可终止实际请求，而不是只让业务层先返回失败。
- 429、离线或协议退避期间，不再每分钟重复触发无意义的 `notifyListeners()` 和页面重建。
- 降低异常网络下多个迟到请求并存的概率，减少额外 radio 活跃时间、socket 占用和迟到响应。

本文不预先承诺具体百分比。CPU、网络 radio 活跃时间和耗电量必须在目标 Android / iOS
真机上测量后才能形成数字结论。

## 2. 不可改变的功能红线

所有优化都必须服从以下约束。任何一项不满足，就不能以“性能优化”名义合入。

### 2.1 Provider 与数据语义

- 不改变 Codex、Claude 的 endpoint、HTTP method、请求头、OAuth scope 或请求体。
- 不减少 Codex usage 与 Reset Credits 请求；两者继续并行，Reset Credits 独立失败不能拖垮
  主额度。
- 不减少 Claude usage 请求；profile 的现有补取条件本轮保持不变。
- 不改变额度解析、窗口识别、`unknown` 保留、剩余百分比、重置时间和身份隔离逻辑。
- 不以降低请求数为由牺牲数据完整性、Reset Credits、套餐名或刷新后的准确性。

### 2.2 刷新与退避

- 自动刷新继续只在前台工作；后台刷新仍不实现。
- 保留 15 / 30 / 60 分钟选项和默认 30 分钟，不擅自延长用户选择的间隔。
- 保留启动读缓存、到期才请求、回到前台检查到期状态的现有行为。
- 保留手动刷新 60 秒节流、429 `Retry-After`、本地指数退避和手动操作不能绕过退避。
- 每个 Provider 的请求继续独立、去重；旧响应不能覆盖重新登录或退出后的新状态。
- 优化后实际发起下一次请求的最早时刻不得早于当前实现，也不得无故晚一个完整刷新周期。

### 2.3 OAuth 与平台生命周期

- 保留 PKCE、state 校验、Provider 固定端口和 Codex 1455 → 1457 回退。
- localhost 继续同时监听 IPv4 / IPv6；不能因为应用短暂进入后台就关闭 listener。
- Android Custom Tabs 提前恢复 Activity 时，仍不能把“回到前台”当作取消；合法 callback、
  显式取消或超时继续决定终态。
- 浏览器服务只能在 OAuth 已进入终态后释放；授权页面仍可能完成 callback 时不得提前解绑或
  停止 loopback server。
- iOS `ASWebAuthenticationSession` 的成功、取消、程序化关闭和 presentation anchor 行为不变。
- Q3 验证工具继续只存在于 Debug 设置页；正式 Release 不新增调试入口。

### 2.4 安全与持久化

- access token、refresh token、id token、authorization code 和 `Authorization` 头不得进入
  日志、错误、性能埋点、测试输出或 URL 之外的持久化位置。
- 不为测量性能记录完整 Provider 响应；真实 fixture 仍必须脱敏。
- 凭据继续只进入 `flutter_secure_storage`；不迁移到普通偏好或内存缓存替代安全存储。
- 不改变账号 identity key、缓存隔离、重新登录清旧快照和退出清理规则。

## 3. 当前调用链与功耗来源

### 3.1 正常刷新链路

```text
应用启动 / 回到前台 / 一分钟调度检查
  → AppController 判断 Provider 是否到期
  → 每个 Provider 独立 refresh flight 去重
  → Secure Storage 读取凭据
  → 必要时刷新 access token
  → Codex: usage + Reset Credits 并行
    Claude: usage + 必要时 profile 并行
  → 解析响应、更新内存状态
  → 写入额度缓存
  → notifyListeners 更新界面
```

正常成功路径的请求频率最低为每 15 分钟一次，默认每 30 分钟一次；应用离开前台后主调度
Timer 会取消。因此本轮不把“刷新系统整体重写”作为优化目标。

### 3.2 Android OAuth 资源链路

当前链路：

```text
open
  → bindCustomTabsService
  → client.warmup
  → newSession
  → launch Custom Tab
  → OAuth callback / 取消 / 超时
  → Dart 清理订阅和 loopback server
  → Activity 继续存活
  → Custom Tabs service 直到下一次 open 或 onDestroy 才解绑
```

问题不在 `warmup` 本身，而在终态后的生命周期。授权进行中保留绑定有助于会话稳定；终态后
继续持有则没有产品价值。

### 3.3 网络超时链路

当前 Provider GET、token refresh POST 和 OAuth token POST 都采用：

```text
client.get/post(...).timeout(15 seconds)
```

`Future.timeout` 生成一个新的超时 Future。超过 15 秒后业务层会得到 `TimeoutException`，但
源 Future 仍可稍后完成。当前依赖锁定为 `http 1.6.0`，它已经提供可取消请求；现有代码尚未
使用 abort trigger。

### 3.4 退避期无效唤醒

Provider 失败后会写入 `_providerHeldUntil`，但一分钟调度器的 `_isDue` 只检查登录状态、凭据
阻断和 `lastSuccessAt`。因此旧快照已经到期时，调度器仍每分钟进入 `refreshProvider`；
`_performRefresh` 虽然会阻止网络请求，却会调用 `_showHeldNotice()` 和 `notifyListeners()`。

结果是：退避正确阻止了网络，但没有阻止无意义的状态通知和页面重建。

## 4. 第一阶段：释放 Android Custom Tabs 资源

### 4.1 目标

OAuth 活动期间保留现有 Custom Tabs 行为；OAuth 成功、取消、失败或超时进入终态后，及时、
幂等地释放 Custom Tabs Session 和 Service 绑定。

### 4.2 涉及文件

- `android/app/src/main/kotlin/com/nanvon/cctrace/mobile/MainActivity.kt`
- `ios/Runner/AppDelegate.swift`
- `lib/q3/browser_bridge.dart`
- `lib/auth/oauth_coordinator.dart`：原则上只复核清理调用，若现有 `finally` 足够则不修改
- `lib/q3/q3_controller.dart`：原则上只复核 Debug 工具终态清理，避免两套行为不一致

### 4.3 推荐实现

1. 在平台通道新增语义明确的 `release` 方法。
2. `OAuthBrowserBridge.dispose()` 在关闭 Dart 事件流之前，以 best-effort 方式调用
   `release`；平台清理失败不能覆盖 OAuth 原始结果。
3. Android `release` 执行：
   - 清除 `browserLaunchPending`、`browserPauseObserved`；
   - 处理或终止尚未完成的 `pendingBrowserOpen`，确保 MethodChannel result 不悬挂；
   - 置空 `customTabsSession`、`customTabsPackage`；
   - 当且仅当确实已绑定时调用 `unbindService`；
   - 重复调用必须安全。
4. Android 现有 `close` 在完成“把应用带回前台”的职责后，也可以调用同一个幂等 release
   helper。这样成功 callback 路径不必等到 Dart 对象最终销毁才释放。
5. iOS 同样实现 `release`，复用 `closeActiveSession(programmatically: true)`。它主要用于
   保持跨平台 MethodChannel 契约一致，不新增 iOS 行为。
6. `onDestroy` 继续保留兜底清理，不能因为新增终态释放而删除。

### 4.4 为什么不影响功能

- 不在 `launchCustomTab` 后立即解绑，只在 OAuth 终态或 bridge dispose 后释放。
- 不关闭 Dart loopback server；server 仍由 `OAuthCoordinator` / `Q3Controller` 按原顺序清理。
- 不把 Android `onResume` 改成取消，因此不破坏当前为 localhost resolver 保留的提前恢复兼容。
- 不改变 Custom Tab package 锁定、session fallback、重定向限制或返回 URI。

### 4.5 主要风险与保护

| 风险 | 保护措施 |
|---|---|
| 过早解绑导致 callback 尚未完成 | 只允许终态或 dispose 调用 release，不在普通 `returned` 事件上直接判定终态 |
| `unbindService` 重复调用异常 | 继续用 `customTabsServiceBound` 保护并捕获已断开场景 |
| pending open 的 MethodChannel result 悬挂 | release 必须统一完成 pending result，不能只清字段 |
| 清理异常覆盖登录成功或原始失败 | Dart 侧和原生侧都采用 best-effort，原结果优先 |
| Q3 与正式 OAuth 行为分叉 | 两者复用同一个 `OAuthBrowserBridge.release` 契约 |

## 5. 第二阶段：让 HTTP 超时真正取消请求

### 5.1 目标

保持现有 15 秒超时、错误分类、请求内容和重试规则不变；唯一变化是到期时同步中止底层请求，
不允许它在业务层已经失败后继续运行。

### 5.2 涉及文件

- `lib/providers/provider_api.dart`
- `lib/auth/oauth_coordinator.dart`
- 可选新增一个仅内部使用的轻量网络 helper，避免两处各自实现不同的取消规则
- `test/provider_api_test.dart`
- `test/oauth_test.dart`

### 5.3 推荐实现

1. 使用 `http.AbortableRequest`，为每个请求创建独立 abort trigger。
2. 用单次 Timer 或延迟 Future 在 15 秒到期时完成 abort trigger。
3. 通过现有长生命周期 `http.Client.send()` 发送请求；不要为每次请求新建和关闭 Client。
4. 将 streamed response 完整转换为现有解析代码需要的 `http.Response`，不改变 JSON 解码和
   HTTP 状态码判断。
5. 在 `finally` 中取消超时 Timer，正常完成后不得再触发 abort。
6. Provider 请求若因本地超时 abort，继续映射为 `ProviderFetchFailureKind.offline`。
7. OAuth token exchange 若因本地超时 abort，继续映射为
   `OAuthFailureKind.tokenExchange`，不新增可能泄露网络细节的用户文案。
8. 保持 token refresh、401 后单次 refresh + retry、429 `Retry-After` 和
   `superseded` 竞争保护不变。

### 5.4 请求契约必须逐项保持

| 请求 | 必须保持的内容 |
|---|---|
| Codex usage | Bearer、`User-Agent: codex-cli`、可选 `ChatGPT-Account-Id` |
| Codex Reset Credits | 与当前相同的认证头，继续和 usage 并行 |
| Claude usage | Bearer、当前 `anthropic-beta` |
| Claude profile | Bearer、`Content-Type: application/json`，失败仍不阻断 usage |
| Codex token refresh | form body、`openid profile email` scope |
| Claude token refresh | form body，不新增 scope |
| Codex code exchange | form body、redirect URI、client ID、PKCE verifier |
| Claude code exchange | JSON body、state、redirect URI、client ID、PKCE verifier |

### 5.5 为什么不影响功能

- 正常在 15 秒内完成的请求不发生任何行为变化。
- 当前业务在 15 秒时已经把请求判为失败；终止底层请求只是让资源生命周期与业务结果一致。
- 不缩短超时、不增加重试、不改变状态码映射，因此不会让正常慢请求比现在更早失败。
- 每个 Provider 仍保留现有 refresh flight 去重；取消不会绕过去重重新发请求。

### 5.6 主要风险与保护

| 风险 | 保护措施 |
|---|---|
| form / JSON 编码与便捷 `post` 不一致 | 对现有请求逐项断言 method、header、content-type 和 body |
| abort 被误判成凭据失效 | 只映射为现有 offline / tokenExchange，不进入 credentials |
| 正常响应到达与 abort 同时发生 | 结果只完成一次；补充边界竞争测试 |
| Reset Credits abort 影响主 usage | 保持当前独立失败和并行聚合方式 |
| 取消后迟到响应覆盖新登录状态 | 保留 auth generation、compare-and-replace 和 superseded 检查 |

## 6. 第三阶段：消除退避期无效通知

### 6.1 目标

Provider 处于 `_providerHeldUntil` 之前时，一分钟自动调度只做常数级判断，不进入
`refreshProvider`、不展示自动提示、不调用 `notifyListeners()`。到期后仍在下一次调度检查或
回到前台时正常刷新。

### 6.2 涉及文件

- `lib/app/app_controller.dart`
- `test/app_controller_test.dart`

### 6.3 推荐实现

1. 保留当前 `_isDue` 对“数据是否到期”的定义，避免影响缓存新鲜度判断。
2. 新增仅供自动调度使用的“当前是否可运行”判断，条件为：
   - `_isDue(provider)` 为真；
   - 不在 `_providerHeldUntil` 之前；
   - 不在 `_credentialRefreshBlocked`；
   - 没有同 generation 的进行中请求。
3. 一分钟调度和 `resumed` 自动刷新使用该判断。
4. 手动 `refreshAll(manual: true)` 保持当前提示行为：退避中拒绝请求，并明确显示剩余等待时间。
5. `refreshProvider` 与 `_performRefresh` 中的现有 held 防线继续保留，作为并发和直接调用的
   第二层保护。
6. 不改变 `[30, 60, 120, 300]` 与 `[60, 120, 300, 900]` 退避序列，也不裁剪 Provider
   返回的更长 `Retry-After`。

### 6.4 为什么不影响功能

当前实现即使每分钟进入 `_performRefresh`，在 held 到期前也不会发网络请求。因此提前在调度
入口跳过，只消除了通知与重建，不改变实际请求时机。

held 到期后，当前实现和优化后实现都要等待下一次一分钟检查；应用在到期后恢复前台时也都
会立即检查。因此不会额外延迟一个完整刷新周期。

### 6.5 不在本阶段改变协议错误策略

协议解析失败当前会按瞬时错误退避，最终每 5 分钟重试。长期协议不兼容时确实会产生额外请求，
但直接改为“协议错误永久停止自动刷新”会影响 Provider 临时异常后的自动恢复。

本轮保留现有策略。若真机或线上证据显示协议错误长期持续，再单独讨论以下方案之一：

- 协议错误按正常 15 / 30 / 60 分钟刷新间隔重试；或
- 本次前台会话暂停，下一次 `resumed` 再试；或
- 明确要求用户手动重试。

没有数据前不提前改变恢复语义。

## 7. 可选第四阶段：倒计时 Timer 的最小收敛

### 7.1 本轮为什么不作为必做项

页面只有两个 Provider 卡片，额度窗口数量很少。每个倒计时每分钟只重建一个小型 `Text`，
没有复杂绘制或持续动画。把所有倒计时改造成共享时钟需要引入新的页面级状态和可见性管理，
代码复杂度可能高于实际收益。

### 7.2 如果前三阶段后仍要继续优化

只做以下最小变化：

- `resetsAt == null` 时不创建 Timer，文本固定为 `--`。
- `resetsAt` 已到期时不继续周期刷新，文本固定为 `<1m`，等待下一次真实额度响应替换。
- `didUpdateWidget` 在 `resetsAt` 从空变为未来时间、或未来时间发生变化时正确重启 Timer。
- 未来重置时间的显示粒度继续是一分钟，不改成更粗粒度。
- 不先引入全局 ticker、第三方状态库或页面架构重构。

这项必须用 widget test 覆盖 Timer 创建、更新和 dispose；如果代码复杂度明显上升，则放弃。

## 8. 本轮明确不做的“优化”

以下做法可能让某个指标更好看，但会影响需求、正确性或可靠性，不应采用：

- 把默认刷新从 30 分钟擅自改成 60 分钟。
- 删除 15 分钟选项，或忽略用户已经保存的刷新设置。
- 为减少请求而不再请求 Reset Credits、Claude profile 或模型级额度窗口。
- 把 Codex usage 和 Reset Credits 从并行改为串行；这会延长 radio 活跃和页面等待时间。
- 每次请求新建 `http.Client` 并立即关闭；这会丢失连接复用，增加握手和耗电。
- 为省电在应用进入后台时立即关闭 OAuth loopback listener；系统浏览器授权本来就会触发
  前后台切换，这会直接破坏登录。
- 把 Android `onResume` 当作 OAuth 取消，或为了尽快释放服务而提前结束授权。
- 去掉缓存、旧快照或重置时间兼容逻辑；这会降低离线可用性和展示准确性。
- 限制或抽样 Provider 响应字段来降低 JSON 解析成本；当前数据量不足以证明有此必要。
- 全局禁用动画或 120 Hz 能力；当前动画短暂、可中断且已适配 reduced motion，静态页面不会
  持续逐帧渲染。
- 为减少重建而让 UI 不再响应刷新、错误、登录或主题状态。
- 引入后台任务、推送服务器或自有代理服务来“降低前台开销”。这会扩大权限、安全和隐私边界。

## 9. 实施顺序与回滚边界

每个阶段独立实施、独立测试，不把三项揉成一次不可定位的大改动。

### S0 · 固化现有契约

- 记录当前相关测试清单和真实请求契约。
- 为缺失的资源释放、真实取消和退避静默行为先补失败测试。
- 不更新 golden；本方案不应产生视觉变化。

### S1 · Android Custom Tabs 释放

- 先实现跨平台 `release` 通道和幂等清理。
- 通过静态检查与平台编译后，再进行 Android 真机 OAuth 矩阵。
- 若出现授权页面提前关闭、callback 丢失或回跳失败，整阶段回滚；不通过延长绑定或修改 OAuth
  判定规则临时绕过。

### S2 · 可取消 HTTP 请求

- 先迁移 Provider GET，再迁移 refresh token POST，最后迁移 OAuth code exchange POST。
- 每迁移一种请求都校验 method、header、body、状态码和异常映射。
- 任一请求契约发生变化就回滚该迁移，不调整 Provider 语义适配新 helper。

### S3 · 退避期静默调度

- 只修改自动调度入口，不重写退避状态机。
- 验证到期请求时机、手动提示和 `resumed` 行为完全一致。

### S4 · 可选 Timer 收敛

- 只有前三阶段通过、且测量仍指向 Timer 时才进入。
- 不能证明收益或实现明显复杂化时直接取消，不为“方案完整”强行实施。

## 10. 自动化验证矩阵

实施阶段需要运行哪些命令，应在实际修改前按项目规则再次取得用户同意。本文只定义验收内容。

### 10.1 Provider 网络

| 场景 | 必须保持的结果 |
|---|---|
| Codex 正常 usage + credits | 两个请求并行；主额度和 credits 均展示 |
| Codex credits 失败 | usage 仍成功；credits 独立降级 |
| Claude 正常 usage + 已有 profile | 只请求 usage |
| Claude 缺 profile | usage 与 profile 并行；profile 失败不阻断 usage |
| token 即将过期 | 先 refresh，再用新 token 请求 usage |
| opaque token 返回 401 | 只 refresh 一次，再重试一次 usage |
| 429 + 秒数 Retry-After | 采用不短于本地退避的时长 |
| 429 + HTTP date | 正确换算时长，不提前请求 |
| DNS / socket / client error | 保留旧快照并进入 offline 退避 |
| 15 秒超时 | 业务返回 offline，底层请求收到 abort，不再迟到完成 |
| 请求期间退出登录 | 迟到结果不得恢复已退出账号或写回缓存 |
| 请求期间重新登录 | 旧 generation 不得覆盖新账号 token、identity 或额度 |

### 10.2 OAuth

| 场景 | 必须保持的结果 |
|---|---|
| Codex 1455 可用 | 使用 1455，合法 callback 成功 |
| Codex 1455 占用 | 回退 1457，不改 redirect 规则 |
| Claude 登录 | 使用固定端口、JSON exchange 和 state |
| Android 提前 resumed | 不判定取消，继续等待 callback / 终态 |
| 合法 callback | code 只在内存交换，完成后释放浏览器资源 |
| provider cancel | 显示原取消结果，释放浏览器资源 |
| 5 分钟超时 | 显示原超时结果，关闭 listener 并释放浏览器资源 |
| 非法 state / 缺 code | 不接受，不泄露请求参数 |
| duplicate / late callback | 不重复交换 token，不覆盖终态 |
| bridge release 重复调用 | 不抛异常、不覆盖原始 OAuth 结果 |
| Activity 销毁 | `onDestroy` 兜底仍能完整释放 |

### 10.3 调度与界面

| 场景 | 必须保持的结果 |
|---|---|
| 当前缓存未到期 | 启动不请求 Provider |
| 缓存已到期 | 启动或 resumed 正常请求 |
| held 未到期 | 自动调度不请求、不通知、不整页重建 |
| held 未到期手动下拉 | 拒绝请求并显示剩余等待时间 |
| held 刚到期 | 下一次一分钟检查或 resumed 正常请求 |
| 15 / 30 / 60 分钟设置 | 各自按原间隔生效 |
| 应用进入后台 | 主刷新 Timer 取消，不新增后台任务 |
| 主题切换 | 系统 / 浅色 / 深色立即正确更新 |
| 正常、旧数据、错误、未登录 UI | 文案、颜色、缓存状态与优化前一致 |

## 11. 真机性能与功耗验收

自动化测试只能证明功能契约，不能证明真实功耗下降。前三阶段完成后至少需要以下真机证据。

### 11.1 Android

推荐工具：Perfetto / System Trace、Android Studio Network Inspector、`dumpsys` 只读诊断和系统
电池统计。目标机仍以项目真实分发设备为准。

#### 场景 A：正常前台静置

- 登录两个 Provider，使用默认 30 分钟刷新。
- 完成一次成功刷新后前台静置至少 35 分钟。
- 确认非刷新时段没有 Provider 网络请求，没有持续帧渲染或高频主线程任务。
- 到期时仍只发生预期的一轮每 Provider 请求。

#### 场景 B：OAuth 资源释放

- 分别覆盖成功、取消、超时和浏览器不可用。
- OAuth 活动时允许存在 Custom Tabs 绑定。
- 进入终态后确认本应用不再持有 Custom Tabs service connection；重复登录仍可正常重新绑定。
- callback、回跳和 Activity 复用必须与优化前一致。

#### 场景 C：弱网与超时

- 使用可控的断网、丢包或本地测试服务制造超过 15 秒的请求，不使用真实 token 做故障注入。
- 超时后确认实际连接被终止，不再继续接收 body，也不会与下一轮请求重叠。
- 每个 Provider 同时最多保留一个有效 refresh flight。

#### 场景 D：长 Retry-After

- 使用 fake gateway 或脱敏测试环境制造 1 小时 held。
- held 期间无 Provider 请求、无每分钟 notice 更新；手动刷新仍显示正确等待时间。

### 11.2 iOS

推荐工具：Xcode Instruments 的 Energy Log、Network、Time Profiler。

- 正常前台静置、一次正常刷新、弱网超时分别记录。
- 确认可取消请求在 iOS client 上同样终止。
- OAuth 成功、取消和程序化关闭后 `ASWebAuthenticationSession` 不残留。
- iOS 未实现后台刷新，进入后台后不应观察到新增的周期 Provider 网络活动。

### 11.3 验收指标

| 指标 | 通过标准 |
|---|---|
| 功能回归 | 第 10 节自动化矩阵全部通过，真机 OAuth 矩阵无新增失败 |
| Custom Tabs | OAuth 终态后服务绑定释放；下一次登录可重新建立 |
| 请求终止 | 本地超时后底层请求停止，不出现迟到响应或并发叠加 |
| 请求次数 | 正常成功路径与优化前一致，不减少必要请求、不新增重试 |
| 退避唤醒 | held 期间自动调度不进入 refresh、不触发 notice 通知 |
| 前台静置 | 非到期时段无 Provider 网络活动，无持续高频 UI 帧 |
| 后台行为 | 不新增后台任务、后台网络或持锁行为 |
| 安全 | 日志、测试和性能数据中无 token、code、Authorization 或原始私有响应 |

CPU 百分比、耗电毫安时和 radio 活跃时间只有在同一设备、同一网络、相同操作脚本下做优化前后
A/B 才有意义。首次启动、Debug/JIT、Release/AOT、屏幕亮度和网络类型必须分开记录，不能混成
一个数字。

## 12. 完成定义

本方案只有同时满足以下条件才算完成：

1. P1、P2 三项推荐改动按独立阶段落地，没有夹带无关重构。
2. 现有接口、刷新、OAuth、缓存、错误和 UI 契约全部保持。
3. 新增测试能证明资源释放、真实 abort 和退避静默，而不只是代码路径被调用。
4. 项目原有相关自动化测试全部通过；任何未运行的验证明确标注。
5. Android 与 iOS 分别记录实际验证状态，不能用 Android 结果代替 iOS。
6. 真机证据确认资源生命周期改善；若测不到收益，保留正确的资源释放修复，但不继续扩大优化。
7. 文档同步记录最终改动、测量方法、设备环境和未完成项。

在真机验收完成前，最多可以写“代码已实现、静态检查或自动化测试通过”，不能写成“功耗已
降低”或“性能优化已在双平台验证”。
