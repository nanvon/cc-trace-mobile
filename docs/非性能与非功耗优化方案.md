# CC Trace Mobile 非性能与非功耗优化方案

> 日期：2026-08-13
> 状态：方案稿，尚未实施
> 审查方式：只读核对当前仓库代码、测试、CI、发布脚本与产品文档
> 明确排除：运行性能、网络性能、启动速度、内存、包体积、CPU、后台耗电与刷新功耗
> 本次未执行：代码修改、依赖安装、`flutter analyze`、`flutter test`、平台构建、模拟器或真机操作

## 1. 结论

**需要优化，而且有必要做，但不需要大改架构或重做视觉。**

当前应用的主链已经具备较好的基础：Provider 分离、OAuth + PKCE、安全存储、旧快照保留、
刷新退避、账号切换竞态保护、签名校验和自动化测试都已经存在。现在最值得投入的不是继续堆
功能，而是补齐以下六类产品质量：

1. **最小权限**：当前 OAuth scope 中仍包含可调用模型、创建 API key 或上传文件等能力；
   应先用真实账号实验削减到“只读取额度所必需”的最小集合。
2. **隐私边界**：token 已在安全存储，但普通额度缓存会连同 `accountHint` 写入
   `SharedPreferences`；完整邮箱没有必要进入普通缓存。
3. **故障恢复与可诊断性**：登录 token 交换的网络、HTTP 和响应格式失败被压成同一句
   “登录交换凭据失败”，用户无法自助排障；设置保存和退出登录的存储失败也没有完整 UI 闭环。
4. **无障碍与自适应**：若干浅色文本对比度明显不足，当前只覆盖 `393 × 852`、默认字号的
   golden；首次登录页和多处横向紧凑布局存在大字体、小屏和横屏溢出的高风险。
5. **发布可信度**：Release workflow 使用可漂移的 Action tag，并允许同一 tag 的 APK 通过
   `--clobber` 被覆盖；已有签名和 SHA-256 校验，但产物来源与不可变性仍可加强。
6. **事实与文档一致性**：README 已写 Android 真机端到端通过，而 2026-07-29 的实施记录仍
   将 Android 真机矩阵列为未完成；这是时间线未同步，不应让读者自己判断哪份才是当前事实。

推荐先做 P0/P1，不做“大而全优化”。完成后，应用会从“功能能用”提升到“权限解释得清、
出错能恢复、发布可核验、更多用户能正常使用”。

## 2. 范围与非目标

### 2.1 本方案包含

- 产品状态与验证证据治理
- OAuth 最小授权和安全说明
- 本地隐私数据分层
- 登录、存储、刷新和退出失败的恢复体验
- 无障碍、文字缩放、小屏、横屏与语义化
- 设置页、帮助、版本与故障排查体验
- 测试覆盖、代码可维护性和发布供应链
- README、Release notes、安全反馈模板与截图

### 2.2 本方案明确不包含

- 性能与功耗审查中的任何事项
- 后台刷新、低额度通知、桌面组件或系统小组件
- 历史曲线、趋势预测和“还能用多久”的推断
- 多账号并存、跨设备同步、桌面端配对或共享凭据
- 自有后端、遥测、远程日志或第三方崩溃上报
- 购买 Apple 开发者账号、TestFlight 或 App Store 分发
- 为未知 Provider 字段预留空卡片、空入口或占位页面
- 未经真实响应验证就修改 Provider 字段、scope、枚举或接口语义

通知、组件和历史趋势都可能有产品价值，但它们依赖后台采样，天然会重新进入性能、功耗和
数据完整性问题。本次不把它们夹带进来。

## 3. 当前做得好的部分

以下能力不建议为了“优化”而重写：

- `AppController` 按 Provider 独立维护刷新、退避、失败和授权代次，旧请求不能覆盖新登录或退出。
- access token、refresh token、id token 由 `flutter_secure_storage` 保存，普通额度缓存不保存 token。
- 新安装标记会清理 iOS Keychain 可能残留的旧凭据，Android 已关闭应用备份。
- loopback 回调校验 path、method 和 `state`，返回页不回显 code、state、token 或原始错误。
- Provider 返回失败时保留旧快照并标记 stale，不把旧数据伪装成最新值。
- Android Release 已校验证书指纹、单一 signer、ABI、版本号和 APK SHA-256。
- 已有解析、OAuth、刷新竞态、缓存和两张核心 golden 测试。

因此，后续改动应沿用现有状态语义与安全纪律，只补缺口，不另起一套状态机或设计系统。

## 4. 只读审查发现

### 4.1 P0：OAuth 授权能力大于产品宣称的“只读额度”

当前代码请求的 scope 包含：

- Codex：`api.connectors.read`、`api.connectors.invoke`
- Claude：`org:create_api_key`、`user:inference`、`user:file_upload` 等

应用自身确实只调用额度和 profile 接口，但“应用当前只做读操作”不等于“取得的 token 只有读权限”。
一旦 token 被意外暴露，额外 scope 会放大损失范围。现有 OAuth 文档已把最小 scope 标为待实调，
说明这是已知且尚未闭环的风险。

**两端的裁剪空间不同，收益重心在 Claude 侧**：

- Claude 的 `org:create_api_key`（创建 API key）是高概率可裁项：新版 Claude Code 官方 scope
  集合已不再请求它（2026-06 外部实现对比）；Anthropic 服务端可能静默丢弃该 scope（授权 6 个只
  授 5 个的公开报告）；订阅用户移除它后登录与使用均正常。`user:file_upload`（上传文件）对本应用
  明确多余，同为高概率可裁项。`user:inference` 的授权文案是“贡献你的订阅用量”，大概率是 usage
  接口必需，不可删。
- Codex 的 `api.connectors.read / invoke` 是 `chatgpt.com/backend-api/*`（含本应用使用的
  `wham/usage` 与 `rate-limit-reset-credits`）的授权前置：外部实现缺少这两个 scope 时请求
  Codex 后端直接 401。因此 Codex 侧大概率**没有可裁剪空间**，实验主要用于证实而非收缩。

**判断**：必须做，但不能直接凭字段名删 scope。应按上文预期逐项裁剪，验证登录、token refresh、
usage 和 Claude profile 都仍成功后再写入正式配置；实验优先从 Claude 的 `org:create_api_key` 与
`user:file_upload` 开始。

### 4.2 P1：完整账号提示进入普通额度缓存

`ProviderViewState.toCacheJson()` 会序列化整个 `identity`，其中包含 `accountHint`；
`SharedPreferencesLocalStore` 再把它写入 `quotaCache.v1`。token 在安全存储里，但完整邮箱属于
可识别个人信息，没有必要和额度快照一起进入普通偏好存储。

**判断**：建议改为缓存 schema v2：

- 普通缓存只保留 Provider、额度窗口、刷新时间、Reset Credits、套餐名和不可逆身份指纹；
- 完整 `accountHint` 只从安全凭据恢复；
- UI 默认显示局部脱敏账号，或提供“隐藏账号信息”设置；
- 读取 v1 时完成兼容迁移，下一次写入自动去除明文账号提示。

### 4.3 P1：登录交换失败无法定位到可执行动作

`OAuthCoordinator._exchangeCode()` 把超时、DNS、TLS、代理、连接异常和所有非 2xx HTTP 状态都
映射为 `OAuthFailureKind.tokenExchange`；界面最终只显示“登录交换凭据失败”。

这符合“不泄露 token 和响应体”的安全要求，但过度收敛后无法判断用户应该：

- 切换 Wi-Fi / 蜂窝网络；
- 检查全局 VPN / TUN，而不是浏览器代理；
- 重新发起一轮新授权；
- 等 Provider 恢复；
- 报告协议变化。

**判断**：保留脱敏原则，同时扩充安全诊断维度。允许进入 UI 或本地诊断页的字段仅限：

- Provider
- 阶段：浏览器、callback、token exchange、usage、profile、secure storage
- 传输类别：timeout、DNS/socket、TLS/client、HTTP、decode
- HTTP status（不含响应体和响应头原文）
- 耗时或耗时区间
- 本地生成的短错误码

严禁记录或复制 code、state、token、Authorization、完整 callback URL、请求体和 Provider 响应体。

### 4.4 P1：设置保存与退出登录缺少失败闭环

`setAppearance()` 和 `setRefreshInterval()` 先修改内存状态，再等待本地写入；写入失败时没有回滚、
没有通知，也可能留下“当前界面已变、重启后恢复旧值”的错觉。`signOut()` 依次删除凭据和缓存，
任一步抛错都可能中断后续 UI 状态更新。

**判断**：把这些操作改成显式事务结果，而不是让 Future 异常从点击回调中逸出。

- 设置保存：明确选择“先落盘再生效”或“乐观更新 + 失败回滚”，推荐后者；
- 退出登录：凭据删除优先，缓存删除失败可继续把当前会话置为已退出，同时提示本地清理未完整；
- 所有失败要有持续可读的提示和重试入口；
- 为存储写失败、删除失败、部分成功和重复点击补测试。

### 4.5 P1：刷新退避按钮没有表达真实可用时间

卡片在 429 后显示“稍后重试”，但按钮仍可点击；若仍处于 `retryAfter`，点击不会发请求，只会在
页首短暂显示另一个提示。用户看不到准确剩余时间，也不清楚点击为何没有发生刷新。

**判断**：直接在卡片内展示“约 N 分钟后可重试”，退避结束前禁用按钮或把按钮变成无操作的
倒计时状态；到期后再恢复“重试”。通知区域应使用 `Semantics(liveRegion: true)`，避免屏幕阅读器
错过四秒后自动消失的消息。

### 4.6 P1：浅色主题存在明确的文字对比度风险

按当前 token 对 `content1 = #ffffff` 做静态对比度计算：

| 组合 | 静态对比度 | 当前典型用途 | 结论 |
|---|---:|---|---|
| `default400 #a1a1aa` / 白色 | 2.56:1 | 10.5–12px 辅助标签 | 不足 |
| `warning #f5a524` / 白色 | 2.04:1 | 12.5px 退避提示 | 不足 |
| `low #f3730e` / 白色 | 2.89:1 | 未登录告警文字 | 不足 |
| `danger #f31260` / 白色 | 4.14:1 | 12.5–13.5px 错误文字 | 小字仍不足 |
| `default500 #71717a` / 白色 | 4.83:1 | 普通辅助文字 | 达到 4.5:1 |
| 深色 `default400 #71717a` / `#18181b` | 3.67:1 | 小型标签 | 小字不足 |

以上只是对纯色 token 的静态计算，不等于 Flutter 的完整无障碍测试；但已经足以证明不能继续把
同一套 warning / low 色同时当“填充色”和“小号正文色”。

**判断**：拆分语义色角色，例如 `warningSurface`、`warningText`、`dangerSurface`、`dangerText`，
保留现有进度条色感，同时让正文和按钮文字达到：普通小字至少 4.5:1，大字至少 3:1。

### 4.7 P1：大字体、小屏与横屏没有验收证据

当前两张 golden 固定在 `393 × 852`、默认文字比例。首次登录页是不可滚动的 `Column`，内容靠底部
排列；主卡片的次级窗口行同时包含固定最小宽度标签、进度条、百分比和倒计时。应用的平台配置
允许横屏，但没有横屏或 200% 文字缩放测试。

**高风险场景**：

- 320–360dp 窄屏；
- 横屏手机的低高度；
- 系统字体 130%、160%、200%；
- 长邮箱、长套餐名和长模型名同时出现；
- 中文粗体 / 高对比度 / 减少动画等辅助设置。

**判断**：不建议简单锁死竖屏来回避问题。主屏可在低高度时改为滚动布局，在宽屏时使用两列
Provider 卡片；次级窗口行在极窄宽度或大字体下切换为两行；首次登录页必须可滚动并保持操作按钮
可达。

### 4.8 P1：自定义信息组件的语义仍不完整

目前对 Codex 卡片增加了 `button / expanded` 语义，这是正确方向，但仍有几个缺口：

- 整张卡片可以展开却没有可见箭头或“查看明细”提示，触屏用户几乎无法发现；
- 屏幕阅读器可能把整张额度卡片当成一个超长按钮，层级不够清晰；
- 缩写 `5HOUR / WEEKLY / ALL` 与 `6d2h / 1h42m` 没有完整中文语义；
- 进度条应明确播报“Provider + 窗口 + 剩余百分比”，不能只依赖视觉位置；
- 状态圆点主要依赖颜色，应该为整体状态提供文字语义。

**判断**：保留紧凑视觉，但为辅助技术提供完整 label/value/hint；将展开操作收窄到
`RESETS` 行或增加轻量 chevron，而不是把整张卡片设为隐藏按钮。

### 4.9 P1：同一 Release tag 的 APK 可以被覆盖

Release workflow 在 Release 已存在时跳过创建，但随后始终执行 `gh release upload --clobber`。
这意味着重跑 workflow 可以在同一 tag 和版本号下替换 APK 与 `.sha256`。即使每次文件内部都通过
签名检查，用户仍无法把“之前下载的 v0.1.6”理解为不可变产物。

**判断**：公开 Release 应一次发布、不可覆盖：

- 已存在同名 Release 或资产时默认失败；
- 若构建失败，修复后递增版本并发布新 tag；
- tag 必须指向允许发布的主线提交；
- APK、`.sha256` 和构建来源证明一起发布；
- Release notes 写清 Android 真机验收状态和 iOS 边界。

### 4.10 P1：GitHub Actions 仍使用可漂移 tag

`actions/checkout@v4`、`actions/setup-java@v4`、`subosito/flutter-action@v2`、
`actions/upload-artifact@v4` 和 `actions/download-artifact@v4` 都没有钉扎完整 commit SHA。
Release job 能接触正式签名材料，因此供应链风险高于普通 CI。

**判断**：全部 Action 钉扎完整 SHA，并在行尾注释人类可读版本；增加 Dependabot 的
`github-actions` 更新 PR。对正式 APK 生成 GitHub artifact attestation，使用户能验证产物来自
哪个仓库、workflow 和 commit。注意 attestation 的前提：当前 `release.yml` 的 android job 没有
`permissions` 声明，实施时必须为 attestation 步骤所在 job 补充
`id-token: write`、`attestations: write`（actions/attest 还需 `artifact-metadata: write`）。

### 4.11 P1：验证状态没有单一真相源

当前 README 写 Android 已完成登录与额度实调的真机端到端验证；较早的
`开发实现与静态验证记录.md` 仍把 Android 真机链路列为待验证。这两条可能分别代表 8 月 4 日后的
新事实与 7 月 29 日的历史快照，但文档没有明确“历史记录”和“当前状态”的关系。

另外，发布文档示例仍使用 `0.1.0+2001`，当前 `pubspec.yaml` 已是 `0.1.6+2007`；示例若不明确
标为示例，很容易被误当当前发布事实。

**判断**：新增一个当前验证矩阵作为唯一入口，历史记录保持日期不改写；README、实施计划和
Release notes 只引用当前矩阵。版本示例改成占位符或明确标注“示例”，避免每次发布都手工同步。

### 4.12 P2：公开产品的帮助与维护入口不足

当前设置页只有账户、主题和刷新间隔，缺少：

- 应用版本与构建号；
- “此应用会做什么 / 不会做什么”的完整说明；
- 非官方接口和官方 CLI client ID 风险；
- 登录、限流、协议变化的故障排查；
- 隐私说明、开源仓库、Issue 入口；
- 安全问题的私下报告方式。

README 仍留有截图占位，`pubspec.yaml` 的 description 还是 `A new Flutter project.`，仓库也没有
`SECURITY.md`、`CHANGELOG.md` 或带脱敏提醒的 Issue 模板。

**判断**：这些不阻塞运行，但会直接影响公开用户是否信任应用、遇到错误时会不会把 token 或
完整响应粘贴到 Issue。应在核心安全和可靠性修复后完成。

### 4.13 P2：中英文产品边界不一致

仓库提供 `README_EN.md`，但应用所有产品文案、OAuth 返回页和错误提示均为硬编码中文。

**判断**：必须二选一并公开说明：

1. 若目标用户包含英文用户，接入 Flutter l10n，首批只做简体中文和英文；
2. 若产品现阶段只服务中文用户，在英文 README 明确标注“应用 UI 仅提供简体中文”。

不建议继续保持“英文 README 看起来可以使用，但安装后全是中文”的模糊状态。

### 4.14 P2：大文件已开始增加改动风险，但不值得单独重构

`usage_screen.dart` 超过 1500 行，`app_controller.dart` 超过 600 行。现在仍能理解，但后续同时
加入无障碍、自适应、诊断和设置事务后，单文件会进一步增加回归面。

**判断**：不要为了行数立即重构。应随对应功能最小拆分：

- `ui/usage/`：卡片、状态告警、格式化、语义 label；
- `app/`：认证操作、刷新调度、通知/诊断状态；
- `domain/`：脱敏错误分类和诊断快照。

每次只拆本阶段会修改的代码，并由现有测试保护；禁止先做全仓结构搬家再开始功能修复。

## 5. 优先级总表

| 优先级 | 工作项 | 必要性 | 主要收益 | 依赖 |
|---|---|---|---|---|
| P0 | OAuth 最小 scope 真实实验与收敛 | 必须 | 降低 token 权限半径，兑现只读原则 | 真实账号、当前 Provider 行为 |
| P1 | 普通缓存移除完整账号提示 | 应做 | 降低本地 PII 暴露 | schema v2 与迁移测试 |
| P1 | 登录/刷新安全诊断分类 | 应做 | 用户可自助排障，不需要敏感日志 | 错误模型设计 |
| P1 | 设置与退出登录失败事务 | 应做 | 避免 UI 状态和落盘状态不一致 | 可注入失败的存储 fake |
| P1 | 退避倒计时与按钮真实状态 | 应做 | 消除“按钮可点但没有刷新” | 复用 `retryAfter` |
| P1 | 对比度、200% 字号和自适应 | 应做 | 无障碍、小屏和横屏可用 | UI 测试矩阵、真机辅助功能 |
| P1 | 语义标签与展开可发现性 | 应做 | TalkBack/VoiceOver 与普通触屏用户都能理解 | 交互确认 |
| P1 | Release 不可覆盖、Action SHA、attestation | 应做 | 发布资产可追溯、签名材料更安全 | GitHub workflow |
| P1 | 当前验证状态单一真相源 | 应做 | 防止 README、Release 与历史记录互相矛盾 | 核对 Android 真机证据 |
| P2 | 应用内帮助、版本、隐私和诊断入口 | 建议 | 提升信任与支持效率 | 可能新增 package info 依赖 |
| P2 | README 截图、SECURITY、CHANGELOG、Issue 模板 | 建议 | 提升公开项目完成度 | 真机截图与支持渠道 |
| P2 | 中英文产品边界 | 条件性 | 避免英文用户预期落差 | 目标用户确认 |
| P2 | 随功能最小拆分大文件 | 条件性 | 降低后续回归面 | 不单独启动重构 |

## 6. 分阶段实施方案

### 阶段 A：证据与边界先收口

**目标**：所有后续优化基于同一组当前事实。

#### A1. 建立当前验证矩阵

建议新增 `docs/当前验证状态.md`，每条记录必须包含：

- 平台与系统版本；
- 应用版本、versionCode、commit、构建类型；
- Provider；
- 场景；
- 日期；
- 结果；
- 证据位置；
- 能证明什么；
- 不能证明什么。

先核对 README 所称 Android 端到端通过对应的真实版本、设备、Provider 和场景。若只验证了
happy path，就不能自动视为 Q3 中“各 3 次 + 取消 + 超时 + 重复回调 + 端口占用”全部完成。

#### A2. 明确历史文档效力

- `开发实现与静态验证记录.md` 保留为 2026-07-29 历史快照；
- 文首增加“当前状态见当前验证矩阵”的链接；
- `实施计划.md` 只保留仍有效的未完成项；
- README 和 Release notes 不再手工复述完整矩阵，只引用当前状态。

#### A3. 修正文档元信息

- `pubspec.yaml` description 改成真实产品描述；
- 发布文档中的 `0.1.0+2001` 明确标为示例或改为占位符；
- README 补真实深浅色主屏和设置页截图；
- README_EN 明确当前 UI 语言边界。

**阶段验收**：任意读者只看一个入口即可回答“Android 哪些场景已验证、iOS 还缺什么、当前版本
是多少”；全文搜索不再出现互相冲突的当前结论。

### 阶段 B：最小权限与本地隐私

**目标**：让“只读额度”同时成立于运行行为、token 权限和本地数据分层。

#### B1. Provider scope 削减实验

每个 Provider 独立执行，顺序固定：

1. 记录当前 scope 的成功基线；
2. 每次只删除一个候选 scope；
3. 重新走完整授权，不能复用旧 token；
4. 验证 code → token、refresh token、usage、Codex account id、Claude profile；
5. 连续成功后才进入下一项；
6. 失败只记录 Provider、scope 集合、HTTP status、阶段、日期，不记录响应体和凭据；
7. 把最终最小集合写入代码和 OAuth 文档。

优先尝试删除能够主动消耗额度或扩大数据访问面的 scope，但最终结论只认真实实验。

#### B2. quotaCache v2

建议数据结构：

```text
quotaCache.v2
└─ providers[]
   ├─ provider
   ├─ identityKey       # 现有不可逆短指纹，用于防止跨账号复用
   ├─ plan              # 允许缓存，不含完整邮箱
   ├─ snapshot
   ├─ resetCredits
   └─ lastSuccessAt
```

迁移规则：

- 继续读 v1；
- 忽略 v1 `identity.accountHint`，不得再写回；
- 安全凭据可读时，从 `TokenBundle.accountHint` 提供当前 UI 身份提示；
- 安全凭据不可读时，不从普通缓存恢复邮箱；
- 下一次成功写缓存后只留下 v2；
- 退出登录同时删除对应安全凭据和 v2 快照。

#### B3. 账号展示隐私

推荐默认显示局部脱敏邮箱，例如 `na•••@example.com`，并在设置中允许“显示完整账号”。若不增加
设置，至少在主屏脱敏、设置页完整显示，兼顾扫一眼隐私和账号确认。

**阶段验收**：检查 SharedPreferences 原始值时不存在完整邮箱、token、code、state 或
Authorization；真实账号切换不会复用旧快照；最小 scope 仍能完成真实主链。

### 阶段 C：故障恢复与安全诊断

**目标**：用户知道失败在哪一步、现在能做什么，同时不扩大日志敏感面。

#### C1. 定义脱敏错误模型

建议领域结构：

```text
SafeFailure
├─ provider
├─ phase
├─ category
├─ httpStatus?
├─ occurredAt
├─ durationBucket?
└─ publicCode
```

`publicCode` 示例：`CDX-TOKEN-NETWORK`、`CLA-USAGE-429`。它只用于帮助文档和 Issue 定位，
不得把内部 URL、请求参数或响应摘要编码进去。

#### C2. 对用户给出下一步

| 类别 | 用户文案重点 | 可执行动作 |
|---|---|---|
| timeout / socket / TLS | 当前网络链路未完成 token 交换 | 换网络、检查全局 VPN/TUN、重新授权 |
| HTTP 400 | 本轮 code / redirect / PKCE 或 Provider 策略不接受 | 重新发起全新授权；持续失败时报错误码 |
| HTTP 401 / 403 | 凭据、scope、地区或 Provider 策略拒绝 | 重新登录；持续失败看帮助 |
| HTTP 429 | Provider 要求降频 | 展示真实剩余等待时间，不允许绕过 |
| HTTP 5xx | Provider 暂时异常 | 保留旧数据，稍后重试 |
| decode / protocol | 响应格式可能变化 | 保留旧数据，引导提交脱敏 Issue |
| secure storage | 本机无法安全保存或删除凭据 | 重试；失败时不要宣称已登录/已退出 |

#### C3. 设置与退出事务

- 设置先更新 UI，落盘失败时回滚，并用持久提示说明“未保存”；
- 退出登录期间禁用同一 Provider 的账户菜单；
- 凭据删除成功后，即使缓存删除失败也不得继续使用旧 token；
- 缓存清理失败要记录安全错误码并允许再次清理；
- 所有按钮都必须在点击后产生可观察结果。

#### C4. 本地诊断页

只展示可安全复制的内容：应用版本、构建号、平台、时间、Provider、阶段、分类、HTTP status、
重试时间和 publicCode。默认不自动复制、不自动上传；复制前再次扫描禁止字段。

**阶段验收**：网络、HTTP 400/401/403/429/5xx、协议解析和存储失败都有不同安全错误码与明确
下一步；诊断文本经过断言，不包含凭据或完整响应。

### 阶段 D：无障碍与自适应

**目标**：在不重做视觉的前提下，让核心操作在大字体、小屏、横屏和屏幕阅读器下可用。

#### D1. 色彩 token 分职

- 进度条色可保留原品牌色；
- 文本另设高对比色；
- disabled 与纯装饰元素可以较弱，但不可承载唯一信息；
- 浅色和深色分别计算，不用一个值简单反转；
- 正常小字 ≥ 4.5:1，大字 ≥ 3:1。

#### D2. 布局断点

建议至少覆盖：

| 场景 | 画布 / 条件 | 布局要求 |
|---|---|---|
| 小屏竖屏 | 320 × 568 | 不溢出，登录页可滚动，按钮可达 |
| 主流竖屏 | 393 × 852 | 保持当前视觉基线 |
| 手机横屏 | 852 × 393 | 内容可滚动或两列，不截断顶部操作 |
| 宽屏 / 平板 | 宽度 ≥ 700 | 两张 Provider 卡片可并列，限制内容最大宽度 |
| 大字体 | text scale 1.3 / 1.6 / 2.0 | 不丢内容或功能，必要时行转列 |

#### D3. 语义设计

- 标题标记 header；
- 额度值播报“Codex 周额度剩余 59%，6 天 2 小时后重置”；
- 缩写只用于视觉，semantics 使用完整中文；
- 退避和登录错误使用 live region；
- Reset Credits 使用独立“查看 N 次重置明细”按钮与 expanded 状态；
- 装饰图标和状态圆点从语义树排除，状态由文字提供；
- 所有 tap target 同时满足 Android 48 × 48 和 iOS 44 × 44 最低值。

#### D4. 自动与人工验收

自动测试增加：

- `textContrastGuideline`
- `labeledTapTargetGuideline`
- `androidTapTargetGuideline`
- `iOSTapTargetGuideline`
- 320 × 568、393 × 852、852 × 393
- light / dark
- text scale 1.0、1.3、2.0
- 正常、首次登录、单 Provider 未登录、stale、429、协议错误、设置页

人工测试增加：

- Android TalkBack；
- iOS VoiceOver；
- 系统最大字体；
- 减少动画；
- 高对比度 / 颜色反转可读性；
- 横竖屏旋转后的状态保持。

**阶段验收**：上述自动 guideline 全部通过；200% 文字下无 RenderFlex overflow、不可达按钮或
内容遮挡；TalkBack / VoiceOver 能按合理顺序完成登录、读额度、刷新、展开明细、进入设置和退出。

### 阶段 E：发布与供应链

**目标**：同一版本产物不可悄悄替换，签名材料和构建来源可核验。

#### E1. Workflow 不可变

- 所有 `uses:` 改为完整 commit SHA，行尾保留版本注释；
- 增加 Dependabot 的 GitHub Actions 更新；
- tag 发布前确认版本匹配且提交来自允许发布的主线；
- 已存在 Release 或同名资产时失败，不使用 `--clobber`；
- 失败后发布新修订版本，不覆盖旧 APK。

#### E2. 构建来源证明

- 对 APK 生成 GitHub artifact attestation（需要为构建 job 补充 `id-token: write`、
  `attestations: write` 权限，参考 §4.10）；
- Release 同时保留 APK、SHA-256 和验证说明；
- README 给出 `sha256`、证书指纹和 attestation 的验证命令；
- Release notes 明确 Android 真机状态、iOS 仅无签名编译还是已真机验证。

#### E3. 安全协作文件

- `SECURITY.md`：支持版本、私下报告方式、禁止公开粘贴的敏感信息；
- bug Issue template：设备/系统/版本/Provider/安全错误码，显著提示不要粘贴 token、code、
  Authorization、callback URL 和原始响应；
- `CHANGELOG.md`：用户可见变化、修复、已知限制；
- Release checklist：版本、测试、真机矩阵、文档、签名、checksum、attestation。

**阶段验收**：同一 tag 的第二次发布会失败；Actions 全部钉扎 SHA；APK 能从 GitHub attestation
验证到目标 commit；Issue 模板不会诱导用户提供敏感日志。

### 阶段 F：产品说明与语言边界

**目标**：用户在应用内就能理解产品能力、风险和自助排障方式。

建议设置页增加“关于与帮助”：

- 版本与构建号；
- 只读行为和本地存储说明；
- 非官方产品、使用官方 CLI client ID 与非公开接口的固有风险；
- 登录与刷新故障排查；
- 开源仓库、隐私说明、普通 Issue 和安全报告入口；
- 复制脱敏诊断。

语言策略建议：若继续维护英文 README，则实现 `zh-Hans` / `en` 两种本地化；否则先在英文 README
明确 UI 仅中文，不急着引入 l10n。无论选择哪条，错误码保持语言无关。

**阶段验收**：新用户不依赖 README 也能回答“应用会访问什么、凭据在哪里、为什么可能失效、
报错后怎么办”；英文用户不会被 README 误导。

### 阶段 G：最小可维护性收敛

只在前述阶段需要编辑相关代码时执行：

- 把时间、窗口和错误文案格式化提为纯函数并补边界测试；
- 把 Provider 卡片、状态告警和 Reset Credits 明细按职责拆文件；
- 把安全诊断模型放入 domain，而不是让 UI 解析异常；
- 为存储与诊断接口保留 fake，便于失败注入；
- 不改变 Provider 解析语义，不顺手重构 Q3 Debug 工具。

**阶段验收**：每次拆分的 diff 都和一个具体功能目标绑定；测试覆盖不下降；不存在仅为了目录整齐的
大规模移动。

## 9. 风险与控制

### 9.1 scope 删多导致真实接口 403

控制：一次只删一个，重新授权，记录 status，不凭名称猜；失败立即回到上一个已通过集合。

### 9.2 cache v2 导致账号或套餐提示丢失

控制：完整账号只从安全凭据恢复；缓存身份指纹继续用于防跨账号；v1 fixture 做迁移测试。

### 9.3 提高对比度破坏原视觉

控制：进度色和文本色分离，不整体换色；以主屏 light/dark golden 和真机观感双重验收。

### 9.4 自适应改造让主流手机密度变松

控制：393 × 852 保持现有基线，只在窄屏、低高度、大字体和宽屏触发重排。

### 9.5 诊断信息重新引入敏感泄漏

控制：使用白名单字段生成诊断，不从异常 `toString()`、响应体或请求对象拼接；为禁止词和 token
形态增加测试。

### 9.6 Release 不可覆盖增加发版次数

控制：接受“错误产物用新 patch 版本修复”的成本，以换取同一版本的可验证与不可变。

### 9.7 国际化扩大维护面

控制：先确认目标用户；若做，只支持简中和英文，不引入未承诺的更多语言。

## 10. 最终完成标准

只有同时满足以下条件，才可称本轮非性能优化完成：

- [ ] 两个 Provider 的最小 scope 有带日期的真实账号证据；
- [ ] 普通偏好存储中不存在完整邮箱和任何凭据；
- [ ] 登录、usage、profile、429、协议和安全存储失败都有脱敏分类与明确下一步；
- [ ] 设置保存与退出登录的失败不会留下 UI / 落盘不一致；
- [ ] 核心页面通过 Flutter accessibility guidelines；
- [ ] 320 × 568、393 × 852、手机横屏和 200% 文字下无内容或功能丢失；
- [ ] TalkBack 与 VoiceOver 可以完成核心任务；
- [ ] 同一 Release tag 的 APK 不可覆盖，Actions 钉扎 SHA，APK 有 provenance；
- [ ] Android / iOS 当前验证状态只有一个权威入口，历史记录不冒充当前状态；
- [ ] README 有真实截图、清晰平台边界和安全反馈入口；
- [ ] 自动化通过与真机通过分别记录，不互相替代；
- [ ] 全程没有引入后台刷新、遥测、自有服务器或跨设备依赖；
- [ ] iOS 方案不以购买 Apple 开发者账号或证书为前提。
