## 1. 目标与结论边界

本任务只回答一个问题：

> 最小 Flutter 应用在 iOS、Android 真机的真实生命周期中，能否通过系统浏览器完成授权，
> 并由应用内 `dart:io HttpServer` 稳定接住 `http://localhost` 回调？

完成本任务后，允许得出的结论只有：

- Flutter 应用能否安装并运行在两台目标真机上。
- iOS `ASWebAuthenticationSession`、Android Chrome Custom Tabs 能否把 Provider 的
  localhost 重定向送到同一台手机里的 Dart server。
- 应用进入浏览器授权界面后，Dart server 是否仍能监听。
- 取消、超时、重复回调、非法回调与端口占用是否有确定结果。
- 免费 Apple ID / Personal Team 的首次部署和 7 天到期后重签路径实际是什么。

本任务**不证明** token 交换、usage 请求、安全存储、刷新调度或产品界面可用。

## 2. 明确不做

- 不交换 authorization code，不请求 token 或 usage。
- 不持久化 token、authorization code、PKCE verifier、state 或完整回调 URL。
- 不实现正式 Provider 接口、登录状态机、安全存储、缓存或额度归一化。
- 不实现额度界面、导航、设计 token、空页面或后续功能入口。
- 不读取或上传对话内容，不读取桌面端 `~/.codex`、`~/.claude` 凭据。
- 不使用 WebView，不用 HTTP client 抓取 authorize 页面。
- 不安装 Android Studio、模拟器、AVD 或新的 iOS Simulator Runtime。
- 不购买 Apple 开发者会员，不创建以付费证书为前提的方案。
- 不借机完成 Q4 的 scope、限流、`is_active` 或 fixture 工作。
- 不修改 ClashBar，不 push。

## 4. 技术方案

### 4.1 总体链路

```text
用户点击验证
  → Dart 先绑定 loopback 端口
  → Dart 生成本轮独立的 state、PKCE verifier / challenge
  → Dart 按 Q2 已验证参数构造 authorize URL
  → MethodChannel 只负责唤起系统浏览器
  → 用户在 Provider 页面登录
  → Provider 重定向到 http://localhost:<port>/<path>
  → 同一台手机内的 Dart HttpServer 收到请求
  → Dart 校验 method、path、state 与 code 是否存在
  → 丢弃 code，只保留非敏感结果
  → 返回固定的成功或失败 HTML
```

### 4.2 为什么不用通用 OAuth 插件

`flutter_appauth`、`flutter_web_auth`、`native_authentication` 一类插件通常把自定义 scheme、
App Link 或 HTTPS callback 截获后直接交回应用。这样即使成功，也不能证明手机内
`HttpServer` 收到了 localhost 请求，偏离 Q3 的证伪目标。

Android Auth Tab 也不能替代：Android 官方文档明确说明 Auth Tab 不允许 `http` callback；
两家 Provider 又都拒绝自定义 scheme，当前 redirect URI 只能是 `http://localhost`。

因此本轮使用最小 Flutter `MethodChannel`：

- iOS：只桥接 `ASWebAuthenticationSession` 的启动、用户取消和主动关闭。
- Android：只桥接标准 `CustomTabsIntent` 的启动，以及浏览器关闭后 Activity 返回前台的事件。
- authorize URL、loopback server、回调解析、计时和结果状态全部在 Dart。

这个桥接不抽象成通用插件，不承载 Provider 协议，不为后续功能预留接口。

### 4.3 iOS 浏览器边界

Apple 当前 `ASWebAuthenticationSession.Callback` 只直接匹配自定义 scheme，或与应用建立
Associated Domains 关系的 HTTPS URL；两者都不能代替 Provider 固定的
`http://localhost` 回调。

本轮的验证方式是：

1. `ASWebAuthenticationSession` 只作为系统认证浏览器。
2. 不让 session 把 localhost 回调截获为应用 callback。
3. 让浏览器实际导航到 `http://localhost`，由 Dart server 成为唯一接收者。
4. Dart 收到有效回调后通知 Swift 关闭 session；用户主动关闭时由 Swift 报告
   `canceledLogin`。

> 待验证：这种配置在 Xcode 26 / 目标 iOS 真机上能否让 localhost 请求真正到达 Dart
> server。Apple 文档只证明 API 能启动认证浏览器，不证明固定 HTTP loopback 会在本项目
> 环境中成功；这正是 Q3 的核心实验，不能提前写成事实。

若失败，只允许用外部 Safari 做一次**诊断性对照**，区分“ASWebAuthenticationSession
回调模型不兼容”和“手机 loopback 本身不通”。对照成功不计为 Q3 通过，也不能静默替换
验收标准。

### 4.4 Android 浏览器边界

Android 使用 `androidx.browser:browser:1.10.0` 的标准 `CustomTabsIntent`，不使用不接受
HTTP callback 的 Auth Tab，也不注册 intent-filter 抢占 localhost 回调。

- Custom Tab 由默认浏览器提供，执行时记录浏览器名称和版本。
- App 启动 Custom Tab 后进入后台；Dart server 必须保持监听。
- 浏览器导航 localhost 后显示 Dart server 返回的固定页面。
- 用户关闭或返回 App 时，Kotlin 只上报“浏览器界面已返回”；是否成功由 Dart server 的
  结果判定，不能用 Activity 恢复事件冒充 OAuth 成功。
- 若设备没有 Custom Tabs 提供方，明确失败并停止，不回退 WebView。

Android 官方资料称 Custom Tabs 会提高调用方进程在使用期间的重要性，但本计划仍以目标
真机实测为准，不把文档能力写成已验证生命周期。

### 4.5 loopback server

Dart 使用 `HttpServer.bind(InternetAddress.loopbackIPv4, port)`：

- 只监听 loopback，不监听 `0.0.0.0`、局域网地址或公网地址。
- redirect URI 始终使用 `localhost` 字面量，不使用 `127.0.0.1`。
- Codex 依次尝试 `1455`、`1457`，两个端口都失败时不打开浏览器。
- Claude 本轮固定 `41999`，与 Q1 / Q4 已验证路径保持一致，减少变量。
- 仅接受 `GET` 和 Provider 对应的精确 callback path。
- Provider 返回 `error` 时只归类为“授权未完成”，不显示或记录原始 error description。
- 缺少或不匹配 `state`、缺少 `code`、错误 path、错误 method 均返回固定错误页并继续监听，
  直到本轮超时或用户取消。
- 第一个合法回调决定本轮成功；后续回调只能增加非敏感的 duplicate count，不能改变结果。
- HTML 响应不回显 query、state、code、账号或错误原文，并带 `Cache-Control: no-store`。
- listener 在成功、取消、超时或显式结束后关闭；state、verifier 和临时 URI 引用随本轮释放。

若某台真机的 `localhost` 只解析到 IPv6，先记录失败证据，再做一次双栈诊断；不得在没有证据
时提前扩大监听地址。

### 4.6 Provider 参数

Provider 端点、client ID、scope、callback path 和额外 authorize 参数逐项照抄
[OAuth 可行性验证 §Q2](OAuth可行性验证.md#q2--authorize-端点和-pkce-参数是什么) 与
`verify/oauth/src/lib.rs` 的已验证值，不重新猜测，也不从低证据等级的 Nowdex 观察文档取值。

每次尝试必须生成新的：

- 32 字节安全随机 state，base64url 无 padding。
- 64 字节安全随机 PKCE verifier，base64url 无 padding。
- `S256` code challenge。

仅引入 Dart 官方发布者维护的 `crypto` 包计算 SHA-256；不引入完整 OAuth SDK 或未验证的
PKCE 小包。即使本轮不换 token，authorize 请求仍必须保留 PKCE，确保验证的是后续可延续的
真实链路。

## 6. 诊断界面

只保留一个验证页，允许显示：

- Provider：Codex / Claude。
- 本轮阶段：idle、binding、browser open、callback accepted、cancelled、timeout、failed。
- 实际监听端口。
- state 是否匹配：是 / 否。
- code 是否存在：是 / 否；绝不显示长度或内容。
- callback 次数与 duplicate count。
- 耗时。
- 非敏感错误类别，例如 `port unavailable`、`browser cancelled`、`state mismatch`。

为覆盖边缘场景，允许提供仅用于 Q3 的诊断操作：

- 正常启动。
- 预占 Codex 1455 后启动。
- 同时预占 1455 / 1457 后启动。
- 发送两次合成的本地回调，验证 first-valid-wins。
- 发送错误 state、缺少 code 的合成本地回调。
- 主动取消当前等待。

合成回调只使用固定的 `code=q3-synthetic`，不得保存或重放真实 authorization code。
验证页必须明确标注“Q3 验证工具，不交换 token”。

## 7. 状态与清理规则

每轮只允许一个 active attempt：

1. 新尝试开始前关闭上一轮 listener、浏览器 session、timeout timer 和端口占用器。
2. 先绑定端口，再生成 authorize URL，最后打开浏览器。
3. 合法回调、用户取消、超时三者竞争时，第一个终态生效。
4. 到达终态后，其余异步事件只能被忽略并计为 late event，不能覆盖首个结果。
5. iOS 因 Dart 成功而主动关闭 session 时，随后收到的 `canceledLogin` 计为 late event，
   不能把成功改成取消。
6. Android 只有在已观察到 Custom Tab 导致的 `onPause` 后，才处理下一次 `onResume`；
   Activity 回到前台时若 Dart 已成功则保持成功，若没有回调则经过短暂 grace period 后才
   判为用户取消，避免生命周期事件先于 socket 回调形成竞态。
7. dispose、热重载或应用退出时必须关闭 listener 和所有测试占用端口。

不依赖热重载完成任何验收；每组正式记录都从冷启动或明确重置后的干净状态开始。

## 9. 验收矩阵

### 9.1 真实 Provider

每次成功必须使用新的 state / verifier，重新启动 listener，并记录端口和耗时。

| 平台 | Provider | 成功 | 用户取消 | 5 分钟超时 |
|---|---|---:|---:|---:|
| Android 真机 | Codex | 3 次 | 1 次 | 1 次 |
| Android 真机 | Claude | 3 次 | 1 次 | 1 次 |
| iOS 真机 | Codex | 3 次 | 1 次 | 1 次 |
| iOS 真机 | Claude | 3 次 | 1 次 | 1 次 |

Codex 每个平台的 3 次成功中，至少 1 次必须预占 1455 并实际通过 1457 完成。另做一次
1455 / 1457 同时占用，完成判定是“浏览器未打开、给出明确失败、占用器可清理”。

### 9.2 本地故障注入

以下每个平台各执行一次，不使用真实 code：

| 场景 | 预期 |
|---|---|
| 同一 synthetic callback 连续两次 | 首次成功，第二次只计 duplicate，不改变终态 |
| state 不匹配后再发合法 synthetic callback | 错误请求不结束本轮，后续合法请求可成功 |
| 缺少 code 后再发合法 synthetic callback | 同上 |
| 主动取消后到达 late callback | 仍保持取消，late event 不覆盖终态 |
| 成功后到达浏览器取消 / Activity resume | 仍保持成功 |

### 9.3 平台记录字段

记录写入后续 `docs/Q3真机验证记录.md`，只包含：

- 日期、Git commit、Flutter / Dart 版本。
- 设备型号与系统大版本；不记录序列号、UDID。

## 10. 完成判定

以下全部满足，S1 / Q3 才能标为通过：

- 两台目标真机都能安装、冷启动最小 Flutter 应用。
- Android debug APK 能通过明确文件直接安装并打开。
- iOS 免费 Apple ID / Personal Team 首次部署步骤有实测记录。
- 四组真实 Provider 矩阵全部达到 3 次成功、1 次取消、1 次超时。

- 两个平台的 synthetic duplicate / 非法 callback 不破坏 first-terminal-wins。
- authorization code 只被判定“存在”，未显示、输出、持久化或交换。
- 没有 token、usage、缓存、正式 Provider、导航或额度界面。
- 7 天到期后的启动表现与重签步骤已经实际复查。
- 真机记录完成，`git diff --check` 通过，工作区内容仅属于本任务。

若当天主链路全部通过但 7 天复查未到时间，只能写：

> Q3 双平台主链路通过；S1 的 Personal Team 到期与重签表现待复查。

不得提前把完整 S1 标为通过。

## 11. 失败判定与复审

### 11.1 先排除的环境问题

- 设备未信任电脑、Developer Mode / USB debugging 未开启。
- Personal Team 未选择或免费签名未建立。
- 浏览器、网络、DNS 或 Provider 登录页暂时不可用。
- 端口被本轮测试占用器之外的进程占用。
- Flutter / Gradle / Xcode 构建环境问题。

### 11.2 技术选型级失败

排除环境问题后，仍出现以下任一项：

- iOS `ASWebAuthenticationSession` 无法把 `http://localhost` 导航送到 Dart server。
- Android Custom Tabs 前后台切换会稳定终止 Dart listener。
- 任一平台成功率达不到每个 Provider 3 / 3。
- 必须用 WebView、代理服务器、上传凭据或高维护成本的双平台原生实现才能继续。

此时停止 S2 及后续产品实现，按 ADR-0002 复审。诊断性外部浏览器对照只能解释原因，
不能把失败改写成通过。

## 12. 停止条件

执行过程中出现以下任一情况立即停止并报告：

- 开始前工作区不干净，且修改不属于本计划。
- `flutter create` 模板准备覆盖未知资产。
- 用户尚未确认应用标识，却即将生成或签名工程。
- 需要执行付费 Apple 会员、购买证书或上传凭据的步骤。
- 需要安装 Android Studio、模拟器、新 iOS Runtime 或修改 ClashBar。
- 需要把真实 code、state、token 或完整 callback URL 写入日志、截图或文件。
- Provider 参数与现有 Q1 / Q2 证据不一致。
- 下载依赖失败，修复需要切换非官方来源或扩大网络配置。
- 浏览器桥接必须扩展为正式 OAuth / Provider 实现才能工作。
- 任一真实响应包含意外敏感内容且无法确认已安全丢弃。
