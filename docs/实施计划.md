## 0 · 2026-07-29 开发顺序变更

原计划把 Q3 设为 S2–S6 的硬前置，是为了尽早证伪移动端 loopback 生命周期。当前没有目标
真机，继续等待不会产生新证据；用户因此明确选择承担返工风险，要求先把所有可静态开发的
正式功能做完。

这次变更只推翻**开发顺序**，不推翻验收标准：

- 默认入口已从 Q3 工具切换为正式用量主屏；Q3 工具只在 Debug 设置页保留。
- OAuth、Keychain / Keystore、真实 usage、限流和 `is_active` 仍以真机或真实响应为准。
- 自动化测试、Android APK 和 iOS 无签名构建都不能替代 Q3 双平台真机矩阵。
- 当前实现、门禁结果和剩余项统一记录在
  [开发实现与静态验证记录](开发实现与静态验证记录.md)。

## 1 · 拆分依据

### 不按模块拆，按「能独立证伪」拆

一个步骤成立的条件是：**跑完它能回答一个此前不知道的问题。** 回答不了新问题的划分
只是把文件分堆，不构成步骤。

按这个标准，「写 Dart 层」「写平台桥接层」这类切法是无效的——它们各自跑完都不产生新事实。

### 顺序按风险倒序，不按用户可见顺序

界面排在最后，尽管它最有成就感、也最容易展示进度。

理由是[移动端额度展示要求.md §8](移动端额度展示要求.md) 那份待确认清单：8 条全部标着
「进入实现前必须有结论」，而它们的答案**必须跑通前一层才拿得到**——`is_active` 语义要真实
响应才能分辨，最小刷新间隔要 token 实测，最小 scope 要调通 usage 才知道。

先写界面意味着在 8 个未知数上一次性押注，且猜错时改动分散在解析层、状态机、文案三处。

### 一个步骤失败时，允许它推翻的东西必须提前写清楚

否则失败会被自然而然地降级成「绕一下」。每一步下面的「失败意味着什么」就是这个用途。

### Q4 的搭车项

Q4 判定只要求「能返回可解析的额度数据」，但同一次请求可以顺带答掉后面几步的输入，
成本接近零。**做 Q4 时一起做掉**：

| 搭车项 | 供给哪一步 | 出处 |
|---|---|---|
| dump 两个 usage 接口的**完整**响应，脱敏存 fixture | S4 | [要求 §9](移动端额度展示要求.md) |
| 试出 `/api/oauth/usage` 的最小安全刷新间隔 | S5 | [要求 §6](移动端额度展示要求.md) |
| 逐项裁剪 scope，确认调通 usage 的最小集合 | S2 | [Q2 最小 scope](OAuth可行性验证.md) |
| 超过 5 小时不发对话后再调一次，看 `session` 的 `is_active` 是否变 `false` | S6 文案 | [要求 §4.2](移动端额度展示要求.md) |

最后一条需要等待 5 小时，**Q4 一开始就要挂上**，不然会变成 S6 的阻塞项。

## 3 · 步骤

### S1 · Q3 真机验证框架

[专项执行方案](S1-Q3真机验证专项计划.md)：先确认应用身份、目标真机和验收矩阵，再允许
创建 Flutter 工程。

> 2026-07-29 执行状态：P1 已完成。因暂不具备目标真机条件，用户明确要求先开发功能，
> P3 静态实现已先行完成；这不替代 P2，也不改变任何真机完成判定。

**目标**：搭建最小 Flutter 工程并装进 iPhone 和 Android 手机，作为 Q3 的唯一验证承载物。
它只验证原生浏览器授权页与应用内 loopback 回调，不能提前演进为产品界面。

**证伪**：Flutter 应用能否在两个平台的真实生命周期中稳定完成系统浏览器授权与 loopback
回调。

[ADR-0002](决策/ADR-0002-Flutter移动端技术栈.md) 把「免费 Apple ID 只能真机签名 7 天」
写成了已接受的代价，但**这件事在本仓库从来没有实测过**。继承的约束不等于验证过的
Flutter 真机部署路径。

**完成判定**：

- iOS：空白验证页在真机上打开，记录重签流程实际要几步、7 天到期后的表现；
  `ASWebAuthenticationSession` 能发起授权并由本地 server 接住回调
- Android：APK 直接安装打开；Chrome Custom Tabs 能发起授权并由本地 server 接住回调
- 两个平台、两个 Provider 各成功 3 次，并各覆盖一次取消场景；Codex 额外覆盖 1455 被占用后
  回退到 1457 的路径

**明确不做**：额度展示、导航、缓存、Token 持久化、usage 请求、Provider 归一化与正式状态机。
只加入 Flutter 初始化、双平台原生工程，以及 Q3 所需的原生浏览器和 loopback 回调最小链路。

**失败意味着**：先区分环境、签名、系统浏览器接入与 loopback 生命周期问题；排除环境后
仍无法稳定完成任一平台链路 → 触发 ADR-0002 复审，不把失败降级为「换个插件试试」。

> 待确认：Flutter 在免费 Apple ID + Xcode 26 下的真机部署路径，以及 `dart:io HttpServer`
> 在两个平台前后台切换时的实际行为。
> 假设错误的影响：如果免费 Apple ID 无法完成真机部署，iOS 侧在
> [ADR-0016](https://github.com/nanvon/cc-trace/blob/main/docs/决策/ADR-0016-不购买Apple开发者账号.md)
> 下无路可走；如果 loopback 生命周期不稳定，则需评估少量 Kotlin / Swift 桥接或复审
> ADR-0002。

### S2 · OAuth 登录闭环

**目标**：把 Q3 / Q4 的验证脚手架转成正式实现——授权、拿 code、换 token、能重复登录。

**证伪**：无新问题。协议层由 Q1 / Q2 验过，平台层由 Q3 验过。这一步是工程化，不是探索。

**完成判定**：两个 Provider 都能从零登录成功，且覆盖 [Q1 硬约束](OAuth可行性验证.md)
列出的失败路径：

- Codex 的 1455 被占 → 退 1457 → 再失败给出明确文案，不静默卡住
- 用户中途取消
- 回调超时
- 重复回调

**明确不做**：token 的持久化——那是 S3，这一步 token 只在内存里活着。

**风险低但不等于工作量小**：四条失败路径都要真的走一遍，这部分比 happy path 长。

---

### S3 · 安全存储

**目标**：token 落进 iOS Keychain / Android Keystore，重启应用后仍能用。

**证伪**：Flutter 侧是否有满足安全纪律的双平台安全存储方案。

[ADR-0002](决策/ADR-0002-Flutter移动端技术栈.md) 已记录安全存储可能需要 Flutter 插件或
少量 Kotlin / Swift 桥接；具体方案至今没有验证。

**完成判定**：杀掉应用重开，不需要重新登录；卸载重装后凭据不残留。

**明确不做**：不为了绕开这一步而把 token 存进普通文件或 localStorage。
[CLAUDE.md §4](../CLAUDE.md) 的纪律在这里没有例外——存不住就是这一步没做完。

**失败意味着**：没有合格插件时需要少量 Kotlin / Swift 桥接，工作量显著上升，应回来
重估整体排期，而不是默默吞掉。

> 待确认：Flutter 生态中满足本项目安全要求的安全存储插件及其双平台成熟度。
> 假设错误的影响：只影响 S3 的工作量估计（用现成插件 vs 自写少量原生桥接），不影响
> OAuth 协议结论。

---

### S4 · Provider 解析与额度归一化

**目标**：两个 usage 接口的响应 → 统一的额度模型。

**证伪**：无。桌面端已于 2026-07-27 在 macOS 真机验证，语义以桌面端
`docs/额度领域模型.md` 和 `src-tauri/src/providers/` 为准。

**这一步可以脱队。** 它不依赖登录、不依赖真机、不依赖 S1–S3，用脱敏 fixture 就能写完测完。
等真机调试的间隙可以做这个。

**完成判定**：

- Codex 按 `primary_window` / `secondary_window` 通用解析，**不假设窗口数量**
- Claude 的 `weekly_scoped` 模型级窗口解析完整，**即使现有验证样本没有**
- `resets_at` 缺失时的保留规则生效
- 覆盖 [要求 §2](移动端额度展示要求.md) 那条原则：「现有验证样本没有」不等于「不实现」

**明确不做**：`unknown` 窗口的界面。解析层怎么处理它留到这一步再定，但不画界面
（[要求 §7](移动端额度展示要求.md)）。

**依赖 Q4 的搭车项**：完整响应 dump。没有它，这一步只能对着手写 fixture 编——
[要求 §9](移动端额度展示要求.md) 已经指出，至今没有任何人见过这两个接口的完整响应。

---

### S5 · 状态机、刷新调度与退避

**目标**：三维状态契约（活动 / 快照新鲜度 / 失败原因）+ 429 退避。

**证伪**：实际限流有多严——[要求 §6](移动端额度展示要求.md) 引的两个 issue 称
`/api/oauth/usage` 的限流严到「making usage monitoring unusable」，但那是第三方观察，
我们未验证。

**完成判定**：

- 打开应用**先展示缓存快照**，再决定是否发请求，不无条件刷新
- 处于退避期时下拉刷新**被拒绝**——不发请求，明确告知「稍后可再刷新」，
  而不是转一圈后失败
- 429 进入退避，手动刷新不能绕过
- Reset Credits 与 `/wham/usage` **并行**发，且独立失败，不拖垮主额度

**明确不做**：后台刷新。它涉及两个平台各自的生命周期与系统限制，本计划不含它；
要做是一个独立决定。

**依赖 Q4 的搭车项**：最小安全刷新间隔。拿不到就只能按严的假设配参数——代价不对称，
高估限流只是刷新慢一点，低估会导致功能整体不可用。

### S6 · 界面

**目标**：按 [原型/额度主屏.html](原型/额度主屏.html) 的 9 种状态实现主屏。

**证伪**：无。样式由原型稿定，token 沿用桌面端且色值逐值一致。

**完成判定**：9 种状态都能在真机上触达（不是截图对比，是真的走到那个状态）。

**明确不做**：

- 不照搬桌面端 `380 × 392` 的密度（[CLAUDE.md §3](../CLAUDE.md)）
- 不为 Codex 卡片补一个不存在的窗口来跟 Claude 卡片对齐（[要求 §3.1](移动端额度展示要求.md)）
- 不留「余额：待确认」这类占位卡片（[要求 §3.3](移动端额度展示要求.md)）

**阻塞项**：`is_active` 的文案取决于它的真实语义，而两种解释导向的用户决策相反
（「不适用」vs「未开始」）。**这一条没有结论之前，模型级窗口那行的文案不定稿**——
但解析和渲染逻辑照做，见 S4。

## 4 · 依赖与并行

```text
Q4 ──┬─→ S2 ─→ S3 ─→ S5 ─→ S6
     │         ↑
S1 ──→ Q3 ───────┘  (S1 是 Q3 的验证承载物；Q3 是 S2 的前置)

S4 全程可并行，只依赖 Q4 的响应 dump
S1 可立即开始；Q3 在 S1 提供的真机框架内执行
```

严格串行的只有 S2 → S3 → S5 → S6 这条链。S1/Q3 与 S4 可以并行推进。

**S1 虽然可以脱队，但建议尽早做完**——它是唯一可能推翻技术选型的一步，越晚发现代价越大。

## 5 · 待确认项的归属

[要求 §8](移动端额度展示要求.md) 的清单挂到步骤上：

| 待确认项 | 由谁回答 | 阻塞谁 |
|---|---|---|
| `is_active` 的真实语义 | Q4 搭车（办法一）或 max 计划账号（办法二） | S6 文案 |
| 两个 usage 接口的完整响应 | Q4 搭车 | S4 |
| Reset Credits 独立接口字段是否与 app-server 摘要一致 | S4 实调 | 仅该行是否需独立请求 |
| `/api/oauth/usage` 最小安全刷新间隔 | Q4 搭车 | S5 参数 |
| Claude 的 `subscriptionType` / `rate_limit_tier` 哪个更可靠 | S4 看完整响应 | S6 计划名展示 |
| Claude 周窗口的真实长度（7 天 vs 72 小时滚动） | 观察 `resets_at` 间隔 | S6 展示名 |
| usage 接口所需的最小 scope | Q4 搭车 | S2 |
| 移动端身份（account id / email）的取得路径 | Claude 已确认 `/api/oauth/profile`；Codex 从 token claim 取得 | 真机验证 profile 响应与账号切换 |

身份路径现已明确：Codex 从 token claim 取得，Claude 按官方客户端调用
`/api/oauth/profile`，使用 `account.uuid` 的哈希判断身份并展示 `account.email`。
真机阶段仍须验证 profile 请求、账号切换与缓存清理。

## 6 · 会推翻本计划的情况

- S1 在排除环境问题后仍失败 → 触发 ADR-0002 复审，本计划整体作废重排
- S3 需要自写双平台原生桥接 → 工作量重估，可能需要先出 Android 单平台版本
- Q4 发现 usage 接口的限流严到无法支撑「打开即刷新」→ S5 和 S6 的交互假设都要重写
- Provider 收紧 client_id 或 redirect_uri → 见 [Q1 结论](OAuth可行性验证.md) 的产品风险一节，
  这是整个方案的前提失效，不是某一步的问题

本文件和其它文档一样可以推翻，理由必须是第一性的（[CLAUDE.md §6](../CLAUDE.md)）。
