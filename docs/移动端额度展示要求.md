## 这份文件是什么

两端相同的部分（三维状态契约、四档余量色、`remainingPercent` 统一 clamp、失败保留旧快照、
身份变化清快照）以桌面端 `docs/额度领域模型.md` 为准，这里不复述。

### 证据等级

本文件每条结论都标注来源。移动端**一次真实响应都还没拿到过**，因此没有任何一条是
「移动端已验证」。

| 等级 | 含义 | 本文中的来源 |
|---|---|---|
| 🟢 一手 | Provider 官方开源代码 | [openai/codex](https://github.com/openai/codex) 仓库、PR、issue |
| 🟡 桌面端已验证 | CC Trace 桌面端真机跑通 | `cc-trace/docs/桌面壳验证记录.md`（macOS，2026-07-27） |

## 0 · 原型稿与视觉方向

**原型稿：[原型/额度主屏.html](原型/额度主屏.html)** —— 9 种状态，393 × 852，浏览器直接打开，
带主题 / 缩放 / 文案切换。写界面时的样式参考以它为准。

它是**设计稿，不是应用代码**：不进 Flutter 应用工程、不参与构建，改动走普通 commit。
稿子里所有数值都是合成数据。

**视觉方向：HeroUI，与桌面端一致。** 桌面端已由 ADR-0012 将视觉方向定为 HeroUI 风格，
`src/styles/tokens.css` 已落地；移动端沿用同一套 token，色值逐值一致。

四档余量色里的 `--low`（浅色 `#f3730e` / 深色 `#ff8a3d`）不是 HeroUI 官方值——官方语义色只有
primary / success / warning / danger / default 五个，没有介于 warning 与 danger 之间的这一档——
但它**已由桌面端 ADR-0017 正式采纳**，不是待定的自造值，移动端直接沿用。

> 沿用的是**设计 token 与形态语言**，不是布局。桌面紧凑面板的 `380 × 392` 密度是给菜单栏挂件
> 设计的，移动端不照搬（[CLAUDE.md](../CLAUDE.md) §3）。

## 2 · 一条贯穿全文的原则

> **「当前账号看不到」不等于「不实现」。**

本版有两处属于这种情况：

- **Codex 的 5 小时窗口**：Provider 侧目前取消了，只返回周窗口。但它随时可能恢复
- **Claude 的模型级周窗口**：pro 计划看不到 Fable / Opus 专项额度，max 计划能看到

两者都**真实存在于 Provider 的响应形态里**，只是当前账号触发不到。解析和渲染逻辑必须完整，
按响应实际返回的内容渲染，**不能硬编码「Codex 只有一个窗口」或「没有模型级窗口」**。

这跟已经砍掉的 `unknown` 窗口是**不同性质**的：`unknown` 是对「Provider 未来可能新增某种
窗口」的假想，没有任何已知触发条件；上面两项是**已知存在的真实形态**。

## 3 · Codex

### 3.1 额度窗口

```text
GET https://chatgpt.com/backend-api/wham/usage
```

按 `rate_limit.primary_window` / `secondary_window` 通用解析，**不假设窗口数量**：

| 现状 | 界面 |
|---|---|
| 只返回周窗口 | 卡片主行显示周窗口，**没有子窗口行** |
| 若 5 小时恢复 | 自动变成主行 5 小时 + 子行周窗口，无需改代码 |

字段：`used_percent`、`reset_at`、`reset_after_seconds`、`limit_window_seconds`、`plan_type`。

> 🟡 桌面端 macOS 2026-07-27 实测 plus 计划只返回一个 weekly 窗口。
> 当时记为「原因不清楚」，现已确认是 **Provider 侧取消了 5 小时窗口**。

**Codex 卡片会明显矮于 Claude 卡片**（Claude 至少有 session + weekly 两行）。
这是真实形态，**不要为了对齐硬拉平**——拉平意味着造一个不存在的窗口，或压缩 Claude 的真实信息。

### 3.2 Reset Credits（重置次数与时间）

```text
GET https://chatgpt.com/backend-api/wham/rate-limit-reset-credits
```

**这是「攒下来的额度重置次数」，不是钱。** openai/codex 的 issue 明确写着：

> This does not involve monetary credits or account balance. The feature tracks
> "banked Codex resets" — a usage allowance mechanism separate from billing.

字段（`rust-v0.142.0` app-server 已暴露 / issue 请求暴露）：

| 字段 | 含义 | 状态 |
|---|---|---|
| `availableCount` | 当前可兑换的重置次数 | 🟢 已暴露 |
| `id` | 单张 credit 标识 | 🟢 issue 请求中 |
| `resetType` | 类型，例如 `codex_rate_limits` | 🟢 issue 请求中 |
| `status` | `available` 或已消耗 | 🟢 issue 请求中 |
| `grantedAt` / `expiresAt` | 发放 / 过期时间 | 🟢 issue 请求中 |

`expiresAt` 是有价值的展示项——官方 issue 的理由是「避免用户在过期前没用掉」。

**位置与加载策略**（与 cc-bar 不同，是刻意的）：

| | cc-bar（桌面） | 移动端 |
|---|---|---|
| 位置 | 设置页展开才加载 | **Codex 卡片底部常驻摘要，点击卡片展开时间明细** |
| 时机 | 懒加载 | 与 `/wham/usage` **并行**发，不串行 |
| 失败 | — | 该行显示 `—`，**不影响主额度快照** |

手机上没有「翻到设置页展开」的耐心；但它必须独立失败，绝不能因为这个接口挂了导致主额度
也不显示。

折叠态继续显示「可用次数 + 最早过期日」。展开态按本地时间显示：

- 所有已知额度窗口的精确重置时间
- 所有 `status: available` credit 的精确过期时间；相同时间可以合并为「N 次」
- `availableCount` 大于实际返回的明细数量时，明确写「接口未提供过期时间」，不补造数据
- 没有 `resetsAt` / `expiresAt` 时分别显示「重置时间未知」/「过期时间未知」

展开只消费本次并行请求已经取得的数据，不额外发请求。卡片从当前高度向下展开，动效必须
可中断并支持连续反向点击；默认无回弹，系统要求减少动态效果时直接切换或仅短暂淡入。

> 🟢 字段来自 [openai/codex PR #28143](https://github.com/openai/codex/pull/28143) 与
> [issue #29618](https://github.com/openai/codex/issues/29618)；接口路径与 cc-bar 的
> `CodexResetCreditsClient` 一致。
>
> > 待确认：`/wham/usage` 直接返回的 credits 摘要与独立接口的字段是否一致
> > （PR 提到 `account/rateLimits/read` 里有个 nullable 的 `rateLimitResetCredits` 摘要，
> > 那是 app-server 的封装，不一定等于 HTTP 接口原样）。
> > 假设错误的影响：仅影响这一行是否需要独立请求，不影响主额度链路。

### 3.3 Codex 账户余额 —— 本版不做

原本要做，因为**找不到数据来源**而放弃。查证结果记在这里，避免以后重查：

- `/wham/usage` → 只有 `plan_type` + `rate_limit`，无余额
- `/wham/rate-limit-reset-credits` → 官方明确说明不涉及金额（见 §3.2 引文）

ChatGPT 确实另有 credits 与消费控制的概念（Business 计划的 credits and spend controls），
但那是另一套计费体系，上述两个接口都拿不到。

将来要做，第一步是先确定余额在哪儿能看到（Nowdex？ChatGPT 网页？），再倒推接口。
在找到接口之前**界面上不给它留位置**——留一张写着「余额：待确认」的占位卡片，
正是 [CLAUDE.md](../CLAUDE.md) §2 要防的东西。

## 4 · Claude Code

```text
GET https://api.anthropic.com/api/oauth/usage
anthropic-beta: oauth-2025-04-20
```

### 4.1 session 与周窗口

| 来源 | 映射 |
|---|---|
| `limits[]` 中 `kind: session` | 5 小时窗口 |
| `limits[]` 中 `kind: weekly_all` | 周窗口（全模型） |
| legacy `five_hour` / `seven_day` | 同上，新旧字段并存时合并为一个窗口 |

字段：`percent`（legacy 为 `utilization`）、`resets_at`、`is_active`。

> 🟡 桌面端 macOS 2026-07-27 实测 pro 计划返回 session + weekly，均正确解析。

### 4.2 模型级周窗口（Fable / Opus 等）

`limits[]` 中 `kind: weekly_scoped`，展示名与 id 从 `scope.model` 或 `scope.surface` 派生。

**必须实现，即使当前账号看不到。** pro 计划没有 Fable 模型，所以 pro 账号的响应里
这一项要么缺席、要么标记为不生效；max 计划或有模型级额度的账号能看到真实数据。

#### `is_active: false` 的展示规则

Provider 对该字段的完整语义仍未公开，但不能再把所有 `false` 都显示成「当前不可用」：

| 窗口类型 | 界面处理 | 理由 |
|---|---|---|
| `session` / `weekly_all` | 保留响应百分比，显示「未开始」 | 这是账号级订阅窗口；没有活动滚动窗口不等于账号没有额度 |
| `weekly_scoped` | 显示 `--` 与「当前不可用」 | 模型级窗口可能确实不适用于当前计划或模型 |

缺失 `is_active` 时仍默认 `true`。这条按窗口类型分流的规则避免把「尚未开始计时」
误报为功能不可用，同时保留模型专项额度不适用的表达。

> > Provider 精确语义仍待确认。两个可验证的办法：
> > 1. 超过 5 小时不发对话后再调一次，看 `session` 的 `is_active` 是否变 `false`
> > 2. 在 max 计划账号上看 `weekly_scoped` 的 Fable 项是否出现且如何标记
> >
> > 假设错误的影响：把「未开始」显示成「不适用」会让用户以为自己没有这个额度；
> > 反过来会让用户以为有个用不了的额度。**两者的用户决策相反**，必须确认后再定文案。

> 🟡 桌面端真机 pro 计划**从未返回过模型级窗口**，因此这个形态两端都没在真实响应里见过；
> 现有 fixture 是桌面端开发者手写构造的，**不能用它推断 Provider 语义**。

### 4.3 不做：Claude 账户余额与 extra_usage

**范围决定，不是技术限制。** Nowdex 没有显示 Claude 账户余额，本版同样不做。

顺带排除 `extra_usage`。它的真实结构已经知道：

```json
"extra_usage": {
  "is_enabled": false,
  "monthly_limit": null,
  "used_credits": null,
  "utilization": null
}
```

这**不是账户余额**，是「订阅额度用完后按 API 价格继续用」的开关、月度上限、已用量和使用率。
本版不展示；将来若要做，它是一个独立的产品决定，不属于「显示还剩多少额度」。

> 🟠 结构来自第三方公开的真实响应记录，未经我们验证。

## 5 · 必须表达的边界状态

### `resets_at` 缺失

`resets_at` 在 Claude 侧经常为 `null`。桌面端为此写了保留规则：新快照缺失、旧快照同一窗口的
`resetsAt` 仍在未来时沿用旧值。

要求：缺失**且无旧值可沿用**时显示「重置时间未知」。

**不能留空。** 留空的那一行会被读成「即将重置」。

> 🟡 桌面端 `额度领域模型.md` §4 保留规则已实现；fixture 中 `null` 大量出现。

## 6 · 刷新策略与 429 ⚠️

`/api/oauth/usage` 的限流可能比预期严厉得多。anthropics/claude-code 有两个 issue 专门反映：

- [#31021](https://github.com/anthropics/claude-code/issues/31021) — persistent 429
- [#31637](https://github.com/anthropics/claude-code/issues/31637) — 「aggressively rate
  limits, **making usage monitoring unusable**」

这直接威胁移动端最基本的交互假设：**打开即刷新 + 下拉刷新**。

要求：

- 下拉刷新**必须能被拒绝**——处于退避期时不发请求，明确告诉用户「稍后可再刷新」，
  而不是转一圈后失败
- 打开应用**先展示缓存快照**，再决定是否发请求，不是无条件刷新
- 429 进入退避，**手动刷新不能绕过**（沿用桌面端规则）

> 🟠 第三方 issue，我们未验证。但代价不对称：**高估限流只是刷新慢一点，低估会导致
> 功能整体不可用**，因此按严的假设设计。
>
> > 待确认：实际的最小安全刷新间隔。Q4 拿到 token 后可以直接测出来。

## 9 · 一个必须记住的解析事实

桌面端用 serde 反序列化，**未知字段被静默丢弃**，且规定「原始响应不入库」。因此
**至今没有任何人见过两个 usage 接口的完整响应**。现有 fixture 全部是手写构造的，不是抓取的。

移动端 Q4 一定要 dump 一次完整响应（脱敏后存 fixture）。这是唯一能回答「接口还返回了什么」
的办法，成本接近零。
