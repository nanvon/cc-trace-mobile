## 2 · 一条贯穿全文的原则

> **「现有验证样本没有」不等于「不实现」。**

本版有两处属于这种情况：

- **Codex 的 5 小时窗口**：Provider 侧目前取消了，只返回周窗口。但它随时可能恢复
- **Claude 的模型级周窗口**：pro 计划看不到 Fable / Opus 专项额度，max 计划能看到

两者都**真实存在于 Provider 的响应形态里**，只是现有验证样本没有触发。解析和渲染逻辑必须完整，
按响应实际返回的内容渲染，**不能硬编码「Codex 只有一个窗口」或「没有模型级窗口」**。

这跟已经砍掉的 `unknown` 窗口是**不同性质**的：`unknown` 是对「Provider 未来可能新增某种
窗口」的假想，没有任何已知触发条件；上面两项是**已知存在的真实形态**。

## 3 · Codex

### 3.1 额度窗口

```text
GET https://chatgpt.com/backend-api/wham/usage
```

按 `rate_limit.primary_window` / `secondary_window` 通用解析，**不假设窗口数量**：

| 现状 | 界面 |
|---|---|
| 只返回周窗口 | 卡片主行显示周窗口，**没有子窗口行** |
| 若 5 小时恢复 | 自动变成主行 5 小时 + 子行周窗口，无需改代码 |

字段：`used_percent`、`reset_at`、`reset_after_seconds`、`limit_window_seconds`、`plan_type`。

> 🟡 桌面端 macOS 2026-07-27 的真实验证样本只返回一个 weekly 窗口。
> 当时记为「原因不清楚」，现已确认是 **Provider 侧取消了 5 小时窗口**。

**Codex 卡片会明显矮于 Claude 卡片**（Claude 至少有 session + weekly 两行）。
这是真实形态，**不要为了对齐硬拉平**——拉平意味着造一个不存在的窗口，或压缩 Claude 的真实信息。

### 3.2 Reset Credits（重置次数与时间）

```text
GET https://chatgpt.com/backend-api/wham/rate-limit-reset-credits
```

**这是「攒下来的额度重置次数」，不是钱。** openai/codex 的 issue 明确写着：

> This does not involve monetary credits or account balance. The feature tracks
> "banked Codex resets" — a usage allowance mechanism separate from billing.

字段（`rust-v0.142.0` app-server 已暴露 / issue 请求暴露）：

| 字段 | 含义 | 状态 |
|---|---|---|
| `availableCount` | 当前可兑换的重置次数 | 🟢 已暴露 |
| `id` | 单张 credit 标识 | 🟢 issue 请求中 |
| `resetType` | 类型，例如 `codex_rate_limits` | 🟢 issue 请求中 |
| `status` | `available` 或已消耗 | 🟢 issue 请求中 |
| `grantedAt` / `expiresAt` | 发放 / 过期时间 | 🟢 issue 请求中 |

`expiresAt` 是有价值的展示项——官方 issue 的理由是「避免用户在过期前没用掉」。

**位置与加载策略**（与 cc-bar 不同，是刻意的）：

| | cc-bar（桌面） | 移动端 |
|---|---|---|
| 位置 | 设置页展开才加载 | **Codex 卡片底部常驻摘要，点击卡片展开过期明细** |
| 时机 | 懒加载 | 与 `/wham/usage` **并行**发，不串行 |
| 失败 | — | 该行显示 `—`，**不影响主额度快照** |

手机上没有「翻到设置页展开」的耐心；但它必须独立失败，绝不能因为这个接口挂了导致主额度
也不显示。

折叠态继续显示「可用次数 + 最早过期日」。展开态按本地时间显示：

- 所有 `status: available` credit 的精确过期时间；相同时间合并为「N 次」
- `availableCount` 大于实际返回的明细数量时，明确写「过期时间未知」，不补造数据

> **2026-07-30 推翻：展开态不再列出额度窗口的精确重置时间。**
> 原文要求「所有已知额度窗口的精确重置时间」。但卡片主体已经逐窗口给了倒计时，
> 展开再把同一份数据换成绝对时刻列一遍是纯冗余，手机上尤其占地方。展开态因此收窄成
> **只补充折叠态没有的信息**，即每批次数各自的过期时刻。
> 连带后果：Codex 卡片只有在 reset credits 有内容时才可展开；没有 credit 数据时
> 整张卡片不可点。

展开只消费本次并行请求已经取得的数据，不额外发请求。卡片从当前高度向下展开，动效必须
可中断并支持连续反向点击；默认无回弹，系统要求减少动态效果时直接切换或仅短暂淡入。
展开不给可见的箭头或「轻点展开」提示（无障碍语义仍标注 button / expanded）——
它补充的是可选信息，不值得在卡片上常驻一个控件。

> 🟢 字段来自 [openai/codex PR #28143](https://github.com/openai/codex/pull/28143) 与
> [issue #29618](https://github.com/openai/codex/issues/29618)；接口路径与 cc-bar 的
> `CodexResetCreditsClient` 一致。
>
> > 待确认：`/wham/usage` 直接返回的 credits 摘要与独立接口的字段是否一致
> > （PR 提到 `account/rateLimits/read` 里有个 nullable 的 `rateLimitResetCredits` 摘要，
> > 那是 app-server 的封装，不一定等于 HTTP 接口原样）。
> > 假设错误的影响：仅影响这一行是否需要独立请求，不影响主额度链路。

### 3.3 Codex 账户余额 —— 本版不做

原本要做，因为**找不到数据来源**而放弃。查证结果记在这里，避免以后重查：

- `/wham/usage` → 只有 `plan_type` + `rate_limit`，无余额
- `/wham/rate-limit-reset-credits` → 官方明确说明不涉及金额（见 §3.2 引文）

ChatGPT 确实另有 credits 与消费控制的概念（Business 计划的 credits and spend controls），
但那是另一套计费体系，上述两个接口都拿不到。

将来要做，第一步是先确定余额在哪儿能看到（Nowdex？ChatGPT 网页？），再倒推接口。
在找到接口之前**界面上不给它留位置**——留一张写着「余额：待确认」的占位卡片，
正是 [CLAUDE.md](../CLAUDE.md) §2 要防的东西。

## 4 · Claude Code

```text
GET https://api.anthropic.com/api/oauth/usage
anthropic-beta: oauth-2025-04-20
```

### 4.1 session 与周窗口

| 来源 | 映射 |
|---|---|
| `limits[]` 中 `kind: session` | 5 小时窗口 |
| `limits[]` 中 `kind: weekly_all` | 周窗口（全模型） |
| legacy `five_hour` / `seven_day` | 同上，新旧字段并存时合并为一个窗口 |

字段：`percent`（legacy 为 `utilization`）与 `resets_at`。响应可能额外包含
`is_active`，但它不属于本应用的归一化额度契约。

> 🟡 桌面端 macOS 2026-07-27 的真实验证样本返回 session + weekly，均正确解析。

### 4.2 模型级周窗口（Fable / Opus 等）

`limits[]` 中 `kind: weekly_scoped`，展示名与 id 从 `scope.model` 或 `scope.surface` 派生。

**必须实现，即使现有验证样本没有。** pro 计划没有 Fable 模型，所以相关响应里
这一项要么缺席、要么标记为不生效；max 计划或有模型级额度的账号能看到真实数据。

#### `is_active` 的处理

Provider 尚未公开这个字段的完整语义，且它不是 Codex 的额度字段。2026-07-30 的真实
Claude 响应已经证明：`session` 可同时出现 `percent: 1`、正在倒计时的 `resets_at` 与
`is_active: false`。因此 `false` 既不能表示「未开始」，也不能表示「当前不可用」。

所有支持的窗口统一按下列规则展示：

| 条件 | 界面处理 |
|---|---|
| 有有效 `percent` | 显示 `100 - percent` 的剩余百分比与进度条 |
| 有 `resets_at` | 显示倒计时 |
| `resets_at` 缺失 | 显示「重置时间未知」 |
| `is_active` 为 `true`、`false` 或缺失 | 不影响上述显示，也不写入缓存 |

`weekly_scoped` 也遵循同一规则：Provider 返回有效百分比就展示该百分比；不能通过
`is_active` 猜测套餐或模型是否适用。鉴权、网络、限流和协议错误仍由 Provider 状态单独表达。

> `is_active` 的变化仍可作为协议观察记录，但不再阻塞 S6 文案，也不再作为产品状态依据。

> 🟡 桌面端真实验证样本**从未返回过模型级窗口**，因此这个形态两端都没在真实响应里见过；
> 现有 fixture 是桌面端开发者手写构造的，**不能用它推断 Provider 语义**。

### 4.3 不做：Claude 账户余额与 extra_usage

**范围决定，不是技术限制。** Nowdex 没有显示 Claude 账户余额，本版同样不做。

顺带排除 `extra_usage`。它的真实结构已经知道：

```json
"extra_usage": {
  "is_enabled": false,
  "monthly_limit": null,
  "used_credits": null,
  "utilization": null
}
```

这**不是账户余额**，是「订阅额度用完后按 API 价格继续用」的开关、月度上限、已用量和使用率。
本版不展示；将来若要做，它是一个独立的产品决定，不属于「显示还剩多少额度」。

> 🟠 结构来自第三方公开的真实响应记录，未经我们验证。

## 5 · 必须表达的边界状态

### `resets_at` 缺失

`resets_at` 在 Claude 侧经常为 `null`。桌面端为此写了保留规则：新快照缺失、旧快照同一窗口的
`resetsAt` 仍在未来时沿用旧值。

要求：缺失**且无旧值可沿用**时显示占位符 `--`。

**不能留空。** 留空的那一行会被读成「即将重置」。

> 🟡 桌面端 `额度领域模型.md` §4 保留规则已实现；fixture 中 `null` 大量出现。
>
> 2026-07-30 起该位置从「重置时间未知」改为 `--`，理由见 §5.1：那一格是紧凑的
> 数字位，一句中文会撑破布局，而 `--` 与其它无值位一致。

### 5.1 术语与时间格式（2026-07-30 定）

界面上反复出现的量（额度窗口名、倒计时、刷新时距）走**缩写**，不写完整中文短句。
理由：这些量在一屏里出现十几次，长句会挤掉真正的读数，也让邮箱之类的次要信息没有余地；
语境已经由所在行给出，「后重置」「窗口」这类词是重复的。

| 量 | 格式 | 例 |
|---|---|---|
| 5 小时窗口 | `5HOUR` | — |
| Codex 周窗口 | `WEEKLY` | — |
| Claude `weekly_all` | `ALL` | 要与同为周窗口的模型级额度区分 |
| Claude `weekly_scoped` | 模型名大写 | `OPUS`、`SONNET` |
| 倒计时 | `<d>d<h>h` / `<h>h<m>m` / `<m>m`，只保留两个量级 | `6d2h`、`1h42m`、`35m` |
| 不足 1 分钟 | `<1m` | — |
| 无时间 | `--` | — |
| 过去时距 | 只保留一个量级 | `1m 前已刷新`、`3h 前的数据` |
| 绝对时刻 | `M/D HH:mm`，跨年补年份，不带后缀 | `8/4 09:00` |

配套排版约束：

- 所有数字位用等宽数位（`FontFeature.tabularFigures`），否则倒计时每分钟刷新会抖动
- 窗口名走小型大写观感：11px / w600 / 字距 +0.7 / `default400`，与大号读数分层
- 主读数的 `%` 单独降到 18px，不与数字同字号

**只有这几类量缩写。** 状态说明、错误提示、按钮仍是完整中文句子——那些是要读懂的，
不是要扫一眼的。

## 6 · 刷新策略与 429 ⚠️

`/api/oauth/usage` 的限流可能比预期严厉得多。anthropics/claude-code 有两个 issue 专门反映：

- [#31021](https://github.com/anthropics/claude-code/issues/31021) — persistent 429
- [#31637](https://github.com/anthropics/claude-code/issues/31637) — 「aggressively rate
  limits, **making usage monitoring unusable**」

这直接威胁移动端最基本的交互假设：**打开即刷新 + 下拉刷新**。

要求：

- 下拉刷新**必须能被拒绝**——处于退避期时不发请求，明确告诉用户「稍后可再刷新」，
  而不是转一圈后失败
- 打开应用**先展示缓存快照**，再决定是否发请求，不是无条件刷新
- 429 进入退避，**手动刷新不能绕过**（沿用桌面端规则）

> 🟠 第三方 issue，我们未验证。但代价不对称：**高估限流只是刷新慢一点，低估会导致
> 功能整体不可用**，因此按严的假设设计。
>
> > 待确认：实际的最小安全刷新间隔。Q4 拿到 token 后可以直接测出来。

### 8.1 Claude 套餐名的来源（2026-07-30 已定位）

**结论：`GET /api/oauth/profile` → `organization.organization_type`，再经一张固定映射表转换。**

```text
claude_pro        → Pro
claude_max        → Max
claude_team       → Team
claude_enterprise → Enterprise
```

映射表以外的取值一律不显示套餐，**不回退、不把内部枚举名摆到界面上**。

证据：Claude Code 2.1.212 的 macOS 可执行文件里，`fetchProfileInfo` 请求
`${BASE_API_URL}/api/oauth/profile`，随后
`subscriptionType = Map([["claude_max","max"],["claude_pro","pro"],
["claude_enterprise","enterprise"],["claude_team","team"]]).get(organization.organization_type)`。
同一函数里 `rateLimitTier = organization.rate_limit_tier` 是**另一个概念**，
取值形如 `default_claude_max_20x`，不能当套餐名用。响应 schema 是
`{account:{uuid,email,…}, organization:{uuid,…}}`，两层都是 passthrough。

已排除的来源，避免以后重查：

| 来源 | 结论 | 依据 |
|---|---|---|
| 桌面端 cc-trace | 移动端用不了 | `providers/claude.rs:524` 取 `credentials.subscription`，它来自 **Claude Code CLI 落盘的** `claudeAiOauth.subscriptionType`（`credentials/claude.rs:170`，macOS 在钥匙串）。桌面端自己从不获取该字段，只在回写时保留（同文件 :243）。**手机上没有那份文件。** |
| Claude token 端点 | 不返回 | 响应为 `token_type / access_token / expires_in / refresh_token / scope / organization{uuid,name} / account{uuid,email_address}`；CLI 在登录后单独调 profile 才补上套餐名 |
| `/api/oauth/usage` 顶层 | 未见过 | `subscriptionType` / `subscription_type` 作为兜底保留在解析器里，真实响应从未命中；`rate_limit_tier` 已从套餐链路中移除（它不是套餐名） |

因此**任何桌面应用都可以直接读 CLI 存好的套餐名，手机不行**——这是数据可得性的差距，
不是实现水平的差距，照搬不了。

实现落点：`lib/providers/provider_api.dart` 的 `_claudePlan` 与 `_requestClaudeProfile`；
套餐名随 `TokenBundle.plan` 一起留存，`_withClaudeProfile` 在套餐名缺失时会重新请求 profile，
token 刷新不会丢掉它。Codex 不走这条路——它的 `plan_type` 每次 usage 响应都带。

> 仍未验证：真机（iOS / Android）上的 profile 响应与账号切换行为。字段路径已定，
> 剩下的是真机验收，见[开发实现与静态验证记录](开发实现与静态验证记录.md)。

## 9 · 一个必须记住的解析事实

桌面端用 serde 反序列化，**未知字段被静默丢弃**，且规定「原始响应不入库」。因此
**至今没有任何人见过两个 usage 接口的完整响应**。现有 fixture 全部是手写构造的，不是抓取的。

移动端 Q4 一定要 dump 一次完整响应（脱敏后存 fixture）。这是唯一能回答「接口还返回了什么」
的办法，成本接近零。
