1. 先读根目录 `AGENTS.md`，再运行 `git status --short`，重新核对本任务涉及的代码。
   本文是上述提交时的方案，不能代替实施时的真实代码。
2. 用户要求“记录到文档”不等于授权实施。后续收到明确的实现指令后，只执行被指定的任务。
3. 每项先确认允许修改的文件与验收条件。本文的“预计涉及文件”用于界定范围，
   不代表可以自动修改所有文件；公共接口变更或超出授权范围，按 `AGENTS.md` 先说明并取得同意。
4. “建议默认方案”是方案作者的推荐，尚非用户确认的产品决策。用户明确要求按该节实现时，
   可按已写明的默认方案执行；标为“待确认”的依赖仍需先解决。
5. 不同时重构状态管理、网络层、OAuth、主题系统或发布流程。保留现有请求去重、
   auth generation、防迟到结果覆盖、凭据隔离、失败保留旧快照、退避和后台停止轮询行为。
6. 不增加 Provider 接口，不猜服务端字段，不使用真实 token、邮箱或原始响应作测试数据。
   本文所有建议新增的本地字段都不是 Provider 响应字段。
7. 不主动提交、发版、运行模拟器或浏览器自动化。编译、测试与平台验证遵守当前仓库授权规则，
   文末命令是待运行建议，不是本次已执行记录。
8. 完成一项就报告改动、验证、未验证项。遇到前提不成立时停在具体问题上，不用占位页面、
   注释掉测试或临时绕过限流来交付。

## 3. T01：统一手动刷新节流文案

### 现状与证据

- `lib/app/app_controller.dart`：`_manualRefreshThrottle` 当前为 10 秒。
- `lib/ui/settings_screen.dart`：设置页仍写“1 分钟节流”。
- `README.md` 也写 1 分钟；实施时同步核对 `README_EN.md` 的对应描述。
- `test/app_controller_test.dart` 已有 `manual refresh is refused during the ten second throttle`。

### 实施步骤

1. 复核控制器当前阈值及适用路径，保持实际刷新行为不变。
2. 修正设置页及中英文 README 的当前功能描述，写清手动刷新节流与 Provider 退避是两层限制。
3. 不全仓替换“一分钟”：自动调度每分钟检查、历史方案、原型占位文案是不同含义。
4. 仅文案变化不新增机械重复测试；不要为了文案另造公共配置层。

预计涉及：`lib/ui/settings_screen.dart`、`README.md`、`README_EN.md`。

### 验收

- 当前产品说明与实际 10 秒配置一致，不承诺 Provider 退避期间也能每 10 秒刷新。
- 控制器和网络请求行为没有改动；历史记录没有被改写成当前事实。

## 4. T02：Reset Credits 独立的新鲜度

### 现状与证据

- `lib/providers/provider_api.dart`：Codex usage 与 Reset Credits 并行请求；后者异常转为 null，
  不阻断 usage 成功。
- `lib/app/app_controller.dart`：`_performRefresh` 在同账号下用旧 `resetCredits` 补空值，
  同时将 Provider 主状态设为 live、更新 `lastSuccessAt`。
- `lib/domain/quota_models.dart`：`ResetCreditsSnapshot` 没有独立采集时间。
- `lib/ui/usage_screen.dart`：`_ResetCreditsRow` 的 stale 来自整张 Provider 卡片。

因此 usage 刷新成功、Reset Credits 请求失败时，旧重置次数可能以正常状态展示。
保留旧值本身正确，缺的是独立的更新时间和失败反馈。不要撤销已有的旧值保留修复。

### 建议默认方案

只为 Reset Credits 增加最小的本地成功时间与本轮更新结果表达；沿用项目状态语义，
不另造 Provider 级 `fresh/stale/error` 总状态。具体字段属于跨层模型变更，先列出方案与影响文件。

| 本轮结果 | 显示要求 |
|---|---|
| usage 成功，Reset Credits 成功且次数为 0 | 显示真实 0 次，更新时间推进 |
| usage 成功，Reset Credits 失败，有旧值 | 保留旧次数，独立变灰，标“重置次数未更新”及可用的旧时间 |
| usage 成功，Reset Credits 失败，无旧值 | 显示暂未获取，不伪造 0 次 |
| usage 失败 | 主卡片继续旧数据语义，不以局部状态掩盖主失败 |
| 从旧版缓存恢复且没有独立时间 | 时间未知；不复制主额度时间冒充该数据的成功时间 |
| 退出或账号变化 | 清理对应数据与新鲜度，不继承上个账号的次数 |

### 实施步骤

1. 明确从 Provider result → Controller → 缓存 → UI 的状态传递；null 不能同时被解释为成功的 0 次。
2. 成功采集时间只在 Reset Credits 请求实际成功时更新；不能在每次 usage 成功时更新。
3. 缓存字段向后兼容，复用现有缓存串行写入与 auth generation 检查。
4. UI 只调整重置次数行及其展开明细的状态，不把整张成功的 usage 卡片判为失败。
5. 保持请求并行、请求头、接口与刷新次数不变；不为了局部失败新增轮询。

预计涉及：`lib/providers/provider_api.dart`、`lib/domain/quota_models.dart`、
`lib/app/app_controller.dart`、`lib/ui/usage_screen.dart`，以及对应 Provider、Controller、
存储和 UI 测试；若修改缓存读写，还需核对 `lib/storage/local_store.dart`。

### 验收

上表各场景都有明确结果；补充失败后恢复、旧缓存兼容、请求期间退出/重登录的验证。
不要只断言新增字段存在，要验证旧值保留与更新时间不被错误推进。

## 5. T03：重置到点体验

### 现状与证据

- `lib/ui/usage_screen.dart`：`_resetLabel` 对所有 `remainingMinutes < 1` 都返回 `<1m`，
  包括重置时间已经过去的情况。
- `_ResetCountdownText` 每分钟更新文字，不负责请求。
- `lib/app/app_controller.dart`：`_isDue` 只按上次成功时间和设置间隔判定，
  `_canAutoRefresh` 再排除退避、凭据阻断和进行中请求。
- `_absoluteTimeLabel` 已有本地时间格式化能力，但目前用于重置次数明细等展示。

### T03-A：到点文案与具体时间

1. 区分 `reset == null`、`0 < reset - now < 1 分钟`、`reset <= now`。
2. 未到点且不足一分钟仍可显示 `<1m`；已到点显示“已到重置时间，待刷新”或含义一致的短文案。
   次级窄行可用“待刷新”，同时给辅助技术完整语义。
3. 轻点倒计时展示本地绝对时间，例如“今天 18:30”；跨日带日期，跨年带年份。
   不直接改变整个应用的英文窗口标签，也不新增独立详情页面。
4. 当前 Codex 整卡轻点会展开重置次数；时间点击应有独立命中范围，不能误触发整卡展开。
5. 旧数据已有提示不能被新的倒计时交互覆盖；时间未知时不造可用入口。

预计涉及：`lib/ui/usage_screen.dart`、`test/usage_screen_test.dart`。

验收：未来 30 秒、恰好到点、过去 10 分钟、空时间、跨日/跨年、旧数据、小屏和大字体。
时间点击与原卡片展开互不干扰，长文案不挤掉百分比。

### T03-B：到点后前台补一次刷新

建议复用现有一分钟调度及恢复前台检查，不新建每窗口网络 Timer，不承诺秒级刷新。

1. 候选触发条件：同账号已知窗口的 `resetsAt` 满足“上次成功采集早于该时间，且当前已到该时间”。
   实施时统一选用成功采集时间口径，并通过可注入的时钟验证。
2. 正常刷新间隔到期或上述条件成立时，都通过现有 `_canAutoRefresh` 保护发起请求。
3. 多窗口同时到点只刷新一次 Provider；已有请求进行中不再启动第二个请求。
4. 若补刷新成功但 Provider 仍返回已过去的同一时间，不能每分钟重复触发。
   可以利用成功采集时间已晚于该 reset 来消除触发条件；不要只检查 `resetsAt <= now`。
5. 刷新失败后保留旧快照，按现有退避重试；退避尚未结束时不绕过限制。
   不在发起请求前就永久标为“已处理”，否则失败后可能不再恢复。
6. 后台不发请求；跨过重置时间后回到前台可检查补刷新。退出/重登录不能继承旧账号的触发状态。
7. 到点本身不代表服务端已经恢复额度；必须等真实响应，不在本地把余量设为 100%。

预计涉及：`lib/app/app_controller.dart`、`test/app_controller_test.dart`；
仅在必要时扩展 `test/test_fakes.dart`。

验收：到点、未到点、同时多窗口、已有请求、429 退避、失败恢复、后台跨点、
成功后仍返回旧 reset、重启加载旧缓存、请求期间账号变化；均核对请求次数和 UI 状态。
同步更新现行重置展示要求，历史方案不倒改。涉及已确认决策时按仓库规则显式确认并补 ADR。

## 6. T04：提示需要注意的额度窗口

### 现状与证据

`lib/ui/usage_screen.dart` 的 `_ProviderCardState.build` 用 `isPrimary` 选择大号数字。
`lib/providers/usage_parsers.dart` 中 Codex 使用服务端主窗口，Claude 优先 session。
主窗口余量高时，周窗口或模型窗口仍可能接近耗尽。

### 建议默认方案与步骤

1. 保持主窗口、次级行和解析器 `isPrimary` 语义，不按余量动态交换大号数字。
2. 在现有卡片中增加至多一条简短提示。默认沿用现有低额度边界：小于 20%，包含 0%。
   这只是额度低提示，不等于预测一定不够用。
3. 从已识别窗口中选剩余比例最低的一项；并列时保持原顺序，避免界面跳动。
4. 提示明确窗口，例如“周额度仅剩 3%，2 天后重置”；0% 写“周额度已用尽”。
   模型窗口要带模型名，不将某个模型额度耗尽说成整个 Provider 不可用。
5. 无重置时间则不拼重置预测；已到点使用 T03 的语义。旧快照不生成当前风险结论，
   保留现有旧数据提示；只有失败提示时避免叠加重复告警。
6. 不合并 Codex 与 Claude 为总额度，不创建综合评分，不新增系统通知。

预计涉及：`lib/ui/usage_screen.dart`、`test/usage_screen_test.dart`。

验收：主窗口 80% / 周窗口 3%、模型窗口 0%、全部不低、恰好 20%、多个低窗口、
旧快照、空快照、未知窗口、无重置时间；主读数和解析契约不变。

## 7. T05：服务显示与顺序

### 现状与证据

`_UsageContent` 固定遍历 `ProviderId.values`。只有一家登录时，另一家仍占一张未登录卡片。
`AppSettings` 目前只保存外观与刷新间隔。现有 UI 测试明确断言未登录卡片仍显示，
因此隐藏功能是行为变更，不能把相关测试失败当作无关问题。

### T05-A：只显示已登录服务

建议在设置页增加“只显示已登录服务”，默认关闭，兼容现有行为。用户开启后只改变主屏显示。

1. 在 `AppSettings` 增加向后兼容的布尔偏好，旧设置缺字段时取 false。
2. 主屏仅在初始化完成后筛选；启动加载态仍正常显示，不因暂未读完凭据闪现空页。
3. 全部未登录时仍显示现有 onboarding，两个登录按钮可达。
4. 设置页账户区域始终保留两家服务的登录入口。
5. 隐藏不等于退出，不删除缓存，不改变调度、凭据或网络请求规则。

预计涉及：`lib/domain/app_settings.dart`、`lib/app/app_controller.dart`、
`lib/ui/settings_screen.dart`、`lib/ui/usage_screen.dart`、存储与 UI 测试。

验收：偏好开/关、零/一/两家登录、旧设置迁移、重启、退出唯一账号后仍可登录。

### T05-B：卡片顺序

当前只有两家服务，建议用“优先显示：Codex / Claude Code”选择，暂不做拖拽排序。
默认 Codex 在前；只影响展示顺序，不修改枚举顺序、存储 key 或刷新顺序。
若以后增加 Provider，再独立设计可排序列表；不在本次为未知服务预留入口。

预计涉及文件与 T05-A 相同。验收偏好持久化、缺字段默认值、与隐藏偏好组合、
卡片 `ValueKey(provider)` 稳定，重排不把一家展开状态转给另一家。

## 8. T06：本地额度变化记录

### 现状与证据

`lib/storage/local_store.dart` 保存每个 Provider 最新快照，没有历史序列。
`QuotaSnapshot` 已有 `capturedAt`，窗口已有 id、kind、remainingPercent、resetsAt、windowSeconds。
`ProviderIdentity.identityKey` 可为空，不能假设所有 OAuth 登录都能识别同一账号。

### 第一版范围

- 仅记录现有成功请求得到的已识别额度窗口，不增加请求频率、不采集后台数据。
- 先显示“较上次减少 8 个百分点”和最近 7 天的实际采样记录；稀疏数据优先列表，
  曲线属于后续展示增强，不是完成第一版的必要条件。
- 本功能表达额度比例变化，不换算 token、消息数、费用，也不声称全天完整消耗。
- 不预测“还能用几小时”；间隔不均、重置和套餐变化会使简单线性预测误导用户。

### 实施前必须确认

> 待确认：是否接受“最多保留 7 天、仅保存在本机、退出对应账号即清除历史”的第一版规则。
> 如果希望退出后保留，需另行设计隐私说明和跨登录身份隔离，不能直接沿用此方案。

> 待确认：身份不可可靠识别时，是否接受每次重新登录开启新的本地记录分组。
> 不能按 Provider 名或套餐合并未知身份，也不要使用 access/refresh token 作为普通存储标识。

### 分阶段实施

1. **规则与纯计算**：先实现相邻记录可比较条件和变化文案，使用合成数据验证。
2. **存储**：增加独立历史存储，不把最新快照缓存改成无限增长数组；明确 schema、7 天清理、
   数量上限、损坏恢复。具体容量上限需在实施方案中给出并解释依据。
3. **采样入口**：仅在成功结果通过 auth generation 检查后记录；历史写入失败不使主额度请求失败。
   用串行写入/失效检查保证退出清理后迟到任务不能重新写回。
4. **展示**：有可用记录后提供真正可用的记录入口；首次记录显示“暂无可比较记录”，
   不画假趋势、不为未实现图表预留空页。

### 比较规则

- 同 Provider、同可靠账号或本地登录分组、同窗口 id/kind，并确认同一周期后才能比较。
- 重置时间改变、跨过已知 reset、窗口长度改变、套餐变化：断开比较，标为新周期或不可比。
- 缺少周期证据时可以展示原始记录，但不输出“消耗了多少”的结论。
- 余量异常上升不能算负消耗；标为“额度增加/周期可能变化”，停止该段消耗推断。
- 相同采集结果不重复写入；不要按百分比相同去掉不同采集时刻的全部记录。
- 只在真实采样时刻画点；长时间未打开应用不插值成完整曲线，不显示“今日总消耗”。
- 不存邮箱、凭据、对话、代码或原始 Provider 响应。只保留必要窗口值、时间及隔离标识。

预计涉及：新增历史模型/纯计算与存储文件（具体命名在实施时确定），
`lib/app/app_controller.dart`、`lib/ui/usage_screen.dart`，必要时新增记录页及对应测试。
先列文件清单和接口再实施，不直接引入数据库或图表依赖。

验收：重复采样、数据缺口、跨周期、缺 reset、套餐/窗口变化、未知账号、重登录、退出清理、

## 9. T07：Android 桌面小组件

### 产品目标

直接在桌面查看两家服务的剩余额度、重置时间和数据更新时间，减少打开应用的次数。
当前未实现；Android 登录期间的前台服务通知不属于额度小组件，也不能拿来长期保活刷新。

### 第一阶段：只做可行性评估

1. 核对当前 Flutter、Android 原生工程与分发配置，确定原生小组件或插件方案。
   此阶段不安装依赖、不改工程；依赖选择时再查官方现行文档。
2. 列出预计文件、桥接方式、展示数据、退出清理方式、测试设备与系统版本。
3. 推荐最小方案：只展示应用最后一次成功快照，应用刷新后更新小组件；点击进入应用。
   明确写数据更新时间，不把缓存称为实时额度。
4. 重置时间已过时显示待刷新；应用未运行时不能本地把额度恢复成 100%。
5. 不把 token 或邮箱传给小组件；小组件存储只含必要的展示数据。
6. 核查退出登录、切账号、重启、应用升级和主缓存清理时的小组件数据失效路径。
7. 可行性报告完成后，由用户确认实施范围；再增加原生组件、桥接和验收。

预计核对：`android/app/src/main/AndroidManifest.xml`、
`android/app/src/main/kotlin/com/nanvon/cctrace/mobile/`、`lib/app/app_controller.dart`、
`lib/storage/local_store.dart`、`pubspec.yaml`。新增文件在评估结论中逐一列明。

### 明确待确认的扩展

- **后台自动刷新**：改变当前前台刷新边界，需单独确认频率、权限、功耗、系统调度限制与 ADR；
  不得承诺准点或实时更新。
- **iOS 小组件**：必须先核实免费 Apple ID 签名、扩展和数据共享的实际可行性。
  不预设已支持，不以购买开发者账号或证书为前提，不用 Android 结果代替 iOS 验收。
- **通知提醒**：本轮没有建议实施。低额度通知依赖新的采样决策，重置提醒也只代表预计时间，
  均需另行提出方案，不能随小组件自动加入。

验收：桌面显示与最近成功快照一致；更新时间明确；点击可达；退出或切账号后旧数据不残留。
编译成功不能代替 Launcher、重启和后台场景的 Android 真机验收。

## 10. T08：同一 Provider 多账号（暂缓）

当前每个 Provider 只有一套活动状态和凭据；设置页支持重新登录、退出登录，
不支持同一家多个账号并存。入口在 `lib/ui/settings_screen.dart`，
凭据在 `lib/storage/credentials_store.dart`，控制器多个 Map 以 `ProviderId` 为 key。

> 待确认：是否经常需要在同一服务的多个账号之间切换，以及需要“切换一个活动账号”
> 还是“多个账号同时展示与刷新”。两者影响范围不同，不能由执行模型自行选择。

确认确有需要后，先设计账号标识、活动账号、凭据 key 迁移、每账号缓存与退避、
请求去重、auth generation 和退出范围。旧单账号数据迁移必须可验证，不能直接更改 key 导致凭据丢失。
不加入跨设备凭据同步，不把邮箱当可靠唯一标识，不将这个任务混入 T05 的显示偏好。

验收至少包括：账号 A 请求迟到不能覆盖 B；删除 A 不影响 B；同 Provider 不同账号凭据、
缓存、历史和限流状态互不串用；旧版迁移不强制全部重新登录。未完成设计前不写产品代码。
